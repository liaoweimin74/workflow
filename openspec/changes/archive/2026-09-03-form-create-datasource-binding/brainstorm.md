## Design Summary

为 form-create 的选项类组件增加“数据源”选项类型。目标组件包括选择器、级联选择器、穿梭框，并覆盖同一选项规则工厂生成配置的其他选项类组件。

用户在现有“选项数据”配置区域选择“数据源”后，显示“配置数据源”按钮并弹出配置页面。配置页面固定包含两个页签：第一个“数据源”页签复用数据表格已有的数据源绑定代码，第二个“字段配置”页签使用四个下拉框配置显示字段、值字段、子节点字段和父节点字段，不使用表格。配置至少支持现有 FORM/SYSTEM/API/WORKFLOW 数据源所需的标识、查询条件，以及将返回记录映射成选项的字段。

渲染时遵循优先级：存在有效数据源绑定时从数据源查询并转换选项；没有数据源绑定时保持现有静态数据、文本、JSON 和远程数据行为不变。数据源配置随表单 schema 持久化，并可在设计器预览和实际渲染中复用。

## Alternatives Considered

### 方案 A：前端扩展选项规则（采用）
- **做法**：扩展 vendor 层的选项规则工厂，新增 datasource 类型和配置组件；通过现有前端数据源 API 查询并在消费端做字段映射。
- **优点**：不修改 form-create 源码；可以复用现有 DataPicker/LookupPicker 配置和数据源 API；保留原有四种选项配置。
- **缺点**：需要处理设计器规则与运行时 schema 的衔接；前端需统一不同数据源返回结构。
- **为何未采用其他方案**：符合“不改动 form-create 源码”和前端扩展优先的约束。

### 方案 B：新增专用后端选项 API
- **做法**：后端增加按数据源定义直接返回标准选项的接口，前端只保存配置并调用该接口。
- **优点**：权限、租户和数据转换可集中处理；前端逻辑较薄。
- **缺点**：需要修改后端 API 和数据源服务；本需求明确优先前端扩展，且会扩大变更范围。
- **为何未采用**：现有统一数据源查询能力已可复用，第一版无需新增后端协议。

### 方案 C：把数据源伪装成 form-create 远程请求
- **做法**：仍使用 `effect.fetch`，仅把数据源配置编译成远程请求参数。
- **优点**：对现有选项规则改动少。
- **缺点**：数据源标识、查询条件和字段映射会被迫编码成 HTTP 配置；不能自然复用 DataPicker/LookupPicker；内部数据源与 API 数据源的调用边界不清晰。
- **为何未采用**：配置模型和运行时语义不匹配，维护成本高。

## Agreed Approach

采用方案 A：在 `frontend/src/vendor` 扩展选项数据规则，增加 `datasource` 配置类型和“配置数据源”弹窗。弹窗第一个“数据源”页签复用数据表格组件的 `DsBindingConfigDialog` 数据源绑定代码，第二个“字段配置”页签提供显示字段、值字段、子节点字段、父节点字段四个下拉框。使用现有 `dataSourceApi` 查询数据，按字段映射生成组件所需的选项结构。数据源绑定与 `effect.fetch` 分开存储，未绑定时不改变现有行为。

## Key Decisions

- 不修改 form-create 依赖源码，只修改项目自己的 vendor 规则、注册和渲染适配层。
- 在现有“选项数据”区域增加“数据源”选项；只有选中该类型时显示“配置数据源”按钮。
- 第一版支持 FORM、SYSTEM、API、WORKFLOW 四类现有数据源。
- 字段映射由用户显式配置：普通选项使用 labelField/valueField；树形选项额外保留层级字段映射能力。
- 数据源绑定存在时使用数据源结果；不存在时保留原选项配置路径。
- 配置必须能被 schema 序列化、设计器重新加载，并在预览/正式渲染中生效。
- 子节点字段与父节点字段不可同时配置；普通选择器只需显示字段和值字段。

## Open Questions

- 级联选择器和树形选项的父子节点字段映射需要在实现计划中明确具体 schema 形状。
- 数据源查询的分页上限、空结果展示和请求失败提示应遵循现有 DataPicker/LookupPicker 约定，避免新增不一致行为。
