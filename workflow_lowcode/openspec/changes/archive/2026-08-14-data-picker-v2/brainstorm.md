## Design Summary

数据引用组件（dataPicker）v2 升级：在保留现有"引用底表记录"能力的基础上，将组件定位明确为**纯引用派**（表单只存被引用记录 id，显示值实时解析，`_text` 降级为展示缓存而非业务数据），并补齐业界标配的引用交互能力（过滤条件双类型、级联不清空、允许新增、跳转查看、悬空降级），同时以轻量方式提供"引用感知"（被引用计数、删除/改列风险警告、配置弹窗增强），**不引入独立的数据源管理模块**。

背景：业务表单底表 v1 已落地（`FormDefinition.type=BUSINESS` + column_config 列映射 + 运行时 DDL 建表 + `BizDataService` 通用 CRUD）。data-picker v1 已实现：数据源选择、显示字段、列表列、单多选、`returnFields` 回填、`dependOn` 级联、两列映射（`<key>` id + `<key>_text` 冗余文本）、resolve API。本次升级基于对业界主流低代码平台（钉钉宜搭、明道云、简道云、飞书多维表格、Airtable、NocoDB）数据引用/关联方案的调研。

## Alternatives Considered

### 方案 A：纯引用（彻底移除 `_text` 冗余列）
- **做法**：底表只存 `<key>` id 一列；所有显示场景（编辑态/审批/列表）一律实时调用 resolve API 解析显示文本；`ColumnTypeMapper`、`BizDataService`、`DataPicker.vue` 全面改造。
- **优点**：数据一致性最强，与"不冗余存储"定位完全一致；无缓存失效问题。
- **缺点**：列表页/只读场景大量引用字段时每次渲染都需批量解析，性能与网络开销增加；已发布表单的 `_text` 列需迁移处理；改动面最大。
- **为何未采用**：用户确认保留 `_text` 作展示缓存——显示准确性以实时 resolve 为准，`_text` 仅作性能兜底，与 Airtable cell format V2（`[{id, name}]`）同款形态。纯引用收益（一致性）已被"resolve 优先"策略覆盖，无需承担迁移成本。

### 方案 B：id + `_text` 展示缓存（Agreed）
- **做法**：存储保持两列不变；`_text` 定位从"业务数据/快照"降级为"展示缓存（非业务数据，可在未来移除）"；显示优先级 = 编辑态/审批实时 resolve（失败回退 `_text`），列表/只读直接用 `_text`。
- **优点**：改动最小、向后兼容（已发布表单不受影响）；编辑准确性靠 resolve 保证，列表性能靠缓存保证；业界有先例（Airtable/NocoDB 展示物化）。
- **缺点**：目标记录 displayField 变化后，历史表单 `_text` 不自动刷新（缓存语义，文档标注）；存在短暂显示不一致窗口。
- **为何采用**：兼顾准确性与性能，符合用户"表单中不冗余存储底表数据（业务语义），但允许展示缓存"的定位；无需迁移已有数据。

### 方案 C：现状不动，另建新组件承载纯引用语义
- **做法**：dataPicker 维持现状（快照+引用混合），纯引用作为新组件（如 LinkField）引入，两组件并存。
- **优点**：完全不动现有实现。
- **缺点**：两个"选数据"组件语义高度重叠，设计器用户难以区分；schema/后端重复。
- **为何未采用**：用户明确 dataPicker 的定位就是"引用、不冗余存储"，应在一个组件内收敛语义，而非再开新组件。

### 关于数据源管理模块的取舍
- **做法选项**：A）新增独立"数据源管理"模块（DataSourceDefinition 实体 + CRUD + 管理页）；B）不建模块，依赖现有"已发布业务表单列表"作为数据源选择入口 + 轻量"引用感知"三件套。
- **取舍**：本项目属"表单优先"派（宜搭/简道云同款：表单即数据源，无独立模块）；当前仅一种数据源类型（BUSINESS 表单），独立模块抽象价值为零且与表单体系重叠维护。真实痛点是"被引用表单被删/改列导致引用悬空"，用**引用感知**（被引用计数标记、删除/改列前风险警告、配置弹窗增强）解决，成本远低于模块。**采用 B**；外部 API 数据源（未来 feature）落地时再抽象 `dataSourceType` 枚举与分发点即可。

## Agreed Approach

1. **定位收敛**：dataPicker = 数据引用组件（引用派）。`<key>` 存 id（业务数据），`<key>_text` 为展示缓存（非业务数据）。显示策略：编辑态/审批实时 resolve 优先（失败回退 `_text`），列表/只读直接用 `_text`。后端 CRUD 对 `_text` 的自动维护保留（尽力而为），不再承担一致性语义。
2. **P1 能力补齐**（业界标配、现状缺失）：
   - 过滤条件升级：`dependOn` → `filters: [{ column, operator, valueType: 'static'|'field', value }]`，支持固定值与当前表单字段动态值混合（宜搭同款）。
   - 级联后已选值保留：条件变化默认不清空已选值（宜搭语义），提供"清空"配置开关（现状为强制清空，与业界预期相反）。
   - 允许新增：弹窗内"新增"入口 → 目标表单快速创建 → 提交后自动选中该记录（宜搭"在关联表单增加数据"同款）。
   - 跳转查看：只读态/列表显示文本可点击跳转目标记录详情。
   - resolve 失败降级：显示原始 id / 悬空标红提示（可配置），不再静默。
   - `_text` 缓存语义文档化：目标 displayField 变化不强制刷新历史 `_text`。
3. **引用感知（轻量三件套）**：
   - 被引用计数：后端统计 column_config 中 dataPicker 引用某表单的数量，表单管理列表显示"被 N 个表单引用"。
   - 删除/改列前风险警告：删除被引用表单、修改被引用 displayField/列 → 前端确认弹窗提示影响范围（发布校验侧已有"引用列被删拦截"，补操作侧警告）。
   - 配置弹窗增强：目标表单选择器加搜索、按分类分组。
4. **明确不做（Non-Goals）**：独立数据源管理模块；外部 API 数据源；双向关联/聚合 rollup/关联本表/子表单内引用（后续阶段）。

## Key Decisions

- **D1（存储语义）**：dataPicker 两列映射不变；`_text` 定位降级为展示缓存（非业务数据）。显示优先级：实时 resolve 优先，`_text` 兜底。
- **D2（过滤条件模型）**：`dependOn` 升级为 `filters[]`（`column` + `operator` + `valueType: static|field` + `value`），向后兼容（`dependOn` 等价于一条 field 型 filter）。
- **D3（级联行为）**：条件变化后已选值默认保留（不清空），可配置为清空并重置回填。
- **D4（允许新增）**：弹窗提供"新增"入口，提交目标表单后自动选中新记录并执行回填。
- **D5（审批快照形态）**：`wf_form_data` JSON 中 dataPicker 值存 `{id, text}`——审批归档是流程历史而非底表数据，不违反"底表不冗余"；审批页零 join 可读。
- **D6（引用完整性）**：create/update 校验 id 存在于目标表单（现状 400 拦截）保留；目标记录事后被删 → resolve 失败走悬空降级显示。
- **D7（引用感知）**：不建数据源管理模块；以"被引用计数 + 删除/改列警告 + 配置弹窗增强"轻量实现。

## Open Questions

- 过滤条件的 operator 集合：v2 先支持 `=`（等值）还是连 `like`/`in` 一起？——倾向 v2 仅 `=`，后续按需扩展。
- 允许新增的权限：沿用"能管理目标表单即能新增"（与 v1 数据范围策略一致）还是细分？——倾向沿用 v1。
- 悬空标红的触发范围：仅编辑态标红，还是列表/只读也标红？——倾向编辑态标红 + 只读显示原始 id，列表用 `_text`。
- 已发布表单的 `filters` 迁移：`dependOn` → `filters[]` 的 schema 迁移是否需要自动脚本，还是仅新配置生效？——倾向向后兼容读取（运行时同时识别两种形态），不强制迁移。
