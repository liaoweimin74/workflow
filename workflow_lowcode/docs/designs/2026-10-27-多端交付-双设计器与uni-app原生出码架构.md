## 1. 为什么要反转一条已锁死的裁定

`2026-10-25` §5.2 末尾有一条明确闭合的复核结论（原文「本案不再开放」）：

> 设计时移动预览采用现案——iframe 手机框 + Vant 自建渲染器，可点选编辑；设计预览与 H5 生产运行时**共用同一 Vant 渲染器**（单实现，无端内端外漂移）。

本文推其中**两条前提**，其余维持：

| 旧前提 | 反转理由 |
|---|---|
| 移动端由「桌面页 + 端覆盖层」推导得出 | 移动不是桌面的缩窄。卡片流、下拉刷新、底部动作栏、字段钻取是**独立的交互资产**，从桌面 rule 推导必然丢语义；实测中覆盖层只能表达"列→槽位"这一小块 |
| 「共用同一 Vant 渲染器」= 无漂移，即交付形态 | 要原生能力（相机、定位、推送、离线）就绕不开 uni-app 编译，Vant 只覆盖 H5 手机浏览器。此时 Vant 渲染器不再是交付物，"单实现无漂移"的立论基础消失 |

**维持有效的旧结论**（本文沿用，不重开）：

- uni-app 组件**无法进设计画布**——项目级编译管线，组件不能在管理端运行时动态挂载（§5.2 第二条）
- 平台内所见即所得预览**只能靠自建渲染器**（§5.2 第二条）
- 小程序运行时壳归 P2（§5.2 第四条）

## 2. 四条路线对比与裁定

### 2.1 设计器形态（用户已裁定：双设计器）

**两套设计界面、一套 schema 格式、分端组件集。** 组件语义名可与 WEB 同名，但实现与形态各端自定——例如 `LookupPicker`：WEB 是表格弹窗多选，移动是卡片列表 + 搜索 + 钻取页。表单设计器留在 WEB 端不动。

### 2.2 画布物料 × 交付形态（Approaches 三选 + 一个演进项）

| 方案 | 画布物料 | 生产交付 | 实时 WYSIWYG | 表现漂移 | 判定 |
|---|---|---|---|---|---|
| 甲 uni-app 画布 | uni-app 组件直接进画布 | uni-app 编译 | ✓ | 无 | ✗ 除 §1 的动态挂载限制外，**跨 frame 拖拽是 fc-designer 死穴**（画布在 iframe 内则拖拽/选中/activeRule 全断） |
| 乙 EP 套 van 皮 | EP 壳 + Vant 样式覆写 | Vant 运行时 H5 | ✓ | 无（仅 H5） | ✗ 拿不到 APP/MP 原生能力，且不是任何端的真实交付物 |
| 丙 Vant 物料 | **批 A/B/C 的 Vant 块进第二个 fc-designer 实例** | H5=Vant 运行时；APP/MP=uni-app 出码 | ✓ | **仅 APP/MP 有** | ✓ **采用（第一步）** |
| 丁 产物预览 | 出码→uni-app 编译 H5 产物进 iframe | uni-app 出码 | ✗（编译往返） | 无 | ○ **演进目标**，待编译服务就绪后在 P2 评估替换丙 |

**丙→丁两阶段**，而非一步到丁：丁的前置是"uni-app 工程化编译服务"先存在（成本高）；丙能立刻复用已交付的 15 个移动渲染文件把移动设计器先跑起来。

### 2.3 关键缓和：H5 是独立渠道，漂移只在 APP/MP

实测渠道模型（`ClientServiceImpl.java:57`）`CHANNEL_TYPES = WEB / H5 / APP / MP`，移动侧集合（`MenuServiceImpl.java:35`）`MOBILE_CHANNEL_TYPES = H5 / APP / MP`。据此：

| 目标渠道 | 交付实现 | 与画布的关系 |
|---|---|---|
| H5 | **Vant 运行时渲染（已交付，零新增成本）** | **画布物料即交付物，无漂移** |
| APP / MP | uni-app 出码 + 编译 | 画布（Vant）≠ 产物（uni-app），**表现漂移不可消除** |

所以本文对"β 预览即交付、无翻译损耗"作**诚实限定**：该性质对 H5 完全成立；对 APP/MP，损耗从「schema→代码的翻译」转移为「Vant 画布 vs uni-app 产物」的视觉差。

**漂移的边界声明**：两端**只保证语义层一致**（同一份 schema、同一套语义类型名、同一份数据源绑定、同一套动作链），**不保证表现层一致**。丁 阶段（产物预览）是消除表现漂移的唯一路径。

## 3. 页面资产模型（核心分叉，待拍板）

现存模型：一条 `wf_page_def` 带 `target_clients` CSV（`PageDefinition.java:71-72`，NULL=仅 portal），`PageAccessGuard` 按「端 ∈ target_clients 且 PUBLISHED」放行。即**一条资产发布到多端**已是现状。双设计器下有三解：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 分端独立记录 + 归组键** | 移动页是新一条 `wf_page_def`，加 `parent_page_id`/`page_group` 与 WEB 页成对；各自 `target_clients` 只含本端 | 需一列归组键；"成对发布/批量运维"要新 UI 聚合 |
| B 单记录双 rule | `schema.rule` + `schema.mobileRule` 并存，一条页面发两端 | 整条链路（parse/contract/emit/reverse/出码对比）都要引入"端"维度；两端节点结构天然不对等，reverse 回导复杂化 |
| C 覆盖层（旧 §5） | 桌面 rule + `channelProfiles` 推导 | ✗ 已否（§1 第一条） |

**推荐 A**：共享的事实源是**数据源**（全局 `sys_data_source`，本就跨端复用）与**字段**，不是**页面结构**——页面结构各端独立设计正是本架构主张。B 会让成熟的出码/回导体系为"端"改一遍，投入产出比差。

待拍板项记入 §9-1。

### 4.1 现状（实测）

## 7. 本轮验证发现的三个缺陷（架构结论的证据基础）

### 7.1 `MobileCardList` van-list 取数死锁 — 已修 `1830e6ee`

Vant 触发加载的时序是「先置位 `loading` → `emit('update:loading', true)` → `emit('load')`」（`vant/es/list/List.mjs:60-62`），组件拿 `loading` 当重入守卫 → 每次加载都在第一行返回 → `loading` 永久 true、`finished` 永不置位、**请求一次都不发**。实测绑 12 条记录的源：`dataRequests=0`、卡死「加载中」。

影响面：设计画布 + 批 C 移动预览 + 任何真实移动页的卡片列表，**此前从未取到过数据**。修法：自持 `inFlight` 标志判重入，`loading` 交还 van-list；未绑源/失败两条出口一并复位 `loading`/`refreshing`。

### 7.2 `MobileCardList` 缺 `sourceId` watcher — **未修**

对照实测，同族三个组件**都有**"数据源变更即重取"的 watcher：

| 组件 | 证据 |
|---|---|
| 桌面 `PageDataCards` | `:171-175` `resolvedRefId` computed + `:431-435` `watch(resolvedRefId)` 清列定义 + `metaLoaded=false` 卸载重挂载 |
| `MobileDataForm` | `:201` `watch(resolvedRefId)` |
| `MobileDataContainer` | `:119` `watch(...)` |
| **`MobileCardList`** | **全文件零 `watch`、零 `onMounted`**（`sourceId` 只在 `:62-69` 作 computed，加载全靠 van-list 发 `load`） |

结论：这不是"设计器共有的既有限制"，而是 **`MobileCardList` 单独的实现遗漏**——它的三个兄弟都实现了这条契约。

**机制比"缺 watcher"更硬**：本组件没有 `onMounted`，首帧加载完全由 van-list 自身 `check()` 发 `load` 驱动；而 `1830e6ee` 的修复在"未绑源"出口置了 `finished.value = true`，van-list 在 `finished` 后 `check()` **永久短路**（`List.mjs:40`）。于是 `sourceId`（`:62-69`，纯 computed 无订阅）从空变非空时，**没有任何路径能再触发一次 `load`** —— 光加 `watch(sourceId)` 而不同步重置 `finished`/`page`/`rows`，依然不会重取。

修法（两步缺一不可）：`watch(sourceId)` → 复位 `finished/page/rows/loading/refreshing` → 再走加载；或按桌面 `PageDataCards` 的思路改 `:key` 卸载重挂载（它正是用 `metaLoaded=false` 达成等价的状态机重置）。非新发明，两种范式仓里都已有。

### 7.3 测试建模失明（元问题，优先级高于单个 bug）

批 B 的 8 例测试用裸 `VanList.vm.$emit('load')` 模拟触发，**跳过 Vant 的 `update:loading` 前置**，等于模拟了一条现实中不存在的调用序列——所以死锁在全绿测试下存活。改为忠实复刻（`update:loading` → `nextTick` → `load`）后 **9 例全红复现**，修复后全绿。

规范：**任何包装 Vant 且依赖 `v-model` 驱动回调的移动组件，测试必须复刻其真实 emit 时序与置位顺序**，不得用裸 `$emit` 捷径。批 A/B/C 其余移动块（MobileDataForm/MobileDetail/MobileDataContainer）需按此复查一遍。
