## Context

当前项目是一个低代码平台，包含页面设计器和表单设计器等组件。数据表格组件 `PageDataTable.vue` 需要连接到数据源来获取数据。

**当前架构：**
1. **全局数据源**：通过 `dataSourceApi` 管理，可以创建、启用/禁用数据源
2. **页面内数据源**：在页面设计器中，用户需要将页面内数据源绑定到全局数据源
3. **数据表格组件**：通过 `dataSourceId`（页面内标识）连接到页面内数据源，再通过 `dsRefId`（全局数据源ID）进行写操作

**问题：**
- 只有页面设计器有数据源配置功能（在 `PageDesigner.vue` 中的弹窗）
- 其他设计器（如表单设计器）缺乏这个能力
- 配置逻辑分散，不利于维护和复用

## Goals / Non-Goals

**Goals:**
1. 创建通用的数据源配置面板组件 `DataSourceConfigPanel.vue`
2. 提供统一的数据源绑定配置界面
3. 让所有设计器（页面设计器、表单设计器等）都能使用
4. 保持现有的页面内数据源架构不变

**Non-Goals:**
1. 不改变数据表格组件的数据获取方式
2. 不修改全局数据源的管理逻辑
3. 不引入新的数据源类型
4. 不改变现有的动作总线机制

## Decisions

### 1. 组件设计决策

**选择：** 创建 `DataSourceConfigPanel.vue` 组件

**理由：**
- 符合单一职责原则：组件专注于数据源配置
- 符合开放封闭原则：对扩展开放，对修改封闭
- 符合接口隔离原则：提供干净的接口

### 2. 组件位置决策

**选择：** `frontend/src/components/business/DataSourceConfigPanel.vue`

**理由：**
- 与业务组件放在一起，便于查找
- 符合项目的目录结构规范

### 3. 接口设计决策

**选择：** 使用 Vue 3 Composition API + TypeScript

**理由：**
- 与项目现有技术栈一致
- 提供更好的类型安全
- 更好的代码组织和复用

### 4. 数据流决策

**选择：** 保持现有的页面内数据源 → 全局数据源的绑定方式

**理由：**
- 保持架构稳定性
- 减少迁移成本
- 符合用户的使用习惯

## Risks / Trade-offs

### 风险

1. **重构风险**：需要修改现有设计器以使用新组件
   - **缓解措施**：渐进式重构，先在页面设计器中验证，再推广到其他设计器

2. **兼容性风险**：新组件需要与现有代码兼容
   - **缓解措施**：保持现有接口不变，只增加新的配置方式

3. **性能风险**：组件可能增加渲染开销
   - **缓解措施**：使用虚拟滚动、懒加载等优化技术

### Trade-offs

1. **开发成本 vs 维护成本**：
   - 开发成本：需要开发新组件并重构现有代码
   - 维护成本：集中管理数据源配置，降低长期维护成本
   - **选择**：接受较高的开发成本，以降低长期维护成本

2. **功能完整性 vs 简洁性**：
   - 功能完整性：提供完整的数据源配置功能
   - 简洁性：保持组件简单易用
   - **选择**：优先保证功能完整性，同时保持界面简洁
