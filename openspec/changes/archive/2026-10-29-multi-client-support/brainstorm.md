## Design Summary

**需求形状**：平台要支持任意业务系统"一套业务模型、多客户端、多交付渠道"的形态——客户端（如平台端/司机端/乘客端）**只是举例，不限定端集合**；每个客户端可开通 WEB / H5 / APP / 小程序等渠道的任意组合。因此"客户端"与"渠道"必须成为**数据模型与基础设施能力**，新增一个端 = 配置 + 发布动作，不改平台代码。

**现状缺口**（recon 结论）：

- 整链路是"单端"假设：仅 PC Web 管理端一个运行态；`sys_menu` 全局一棵树；`wf_page_def` 无端/渠道字段
- 唯一端侧先例是小程序（V64 `sys_user_openid` + `/api/auth/miniprogram/login|bind` + ROLE_CUSTOMER），"身份绑定式"特例，未泛化
- 后端 `ChannelType` 是消息通知通道，与交付终端无关（命名区分）
- 表单/页面 schema 由 Element Plus 桌面组件集渲染，混有桌面渲染细节（列宽、栅格 span）

**支撑五层**：① 客户端×渠道建模（`sys_client` / `sys_client_channel`）；② 身份认证泛化（一套 `sys_user` 账号池 × N 种登录方式，token 带 client+channel）；③ 访问控制加端维度（菜单按端分树、角色挂端、数据范围字段策略）；④ 资产 schema 分层 + 多端渲染（逻辑 schema 唯一 + 渠道模板映射 + 端覆盖层）；⑤ 按渠道发布管线（H5 直发 / 小程序审核 / APP 壳+热更）。

**菜单组织**：存量 `sys_menu` 树 100% 归属默认"平台客户端"（只加 `client_id` 列回填，path/权限码/授权全部不动）；客户端管理页按 V66 口径归**开发管理**；菜单管理页加"端"作用域 Tab；端形态约束——WEB 端保持目录/菜单/按钮三层，移动端为**底部 Tab（2~5 个一级菜单）+ 工作台宫格**，同一棵树的两种映射。

**能力被引用而非复制**：司机端"待办"是新建发布到司机端的移动形态页面（引用同一套流程 API），不是共享 PC 页面；隔离靠"资产发布范围 × 端树挂接"两道闸（`PageAccessGuard` 粒度升级为 (client, page)）。

**权限分层**：角色**挂单一端**（`sys_role.client_id` 强隔离）；脱敏并入数据范围——grant 增加字段策略（列→可见/脱敏[内置规则]/隐藏），生效在服务端序列化层，一次封死详情/导出/开放 API 三条泄漏路径。

**渲染分层**：三层区分——组件集（渲染器级：语义类型→按渠道模板映射）、布局（配置级：列→卡片槽位、字段显隐、排序，缺省自动映射）、交互骨架（框架级：弹窗→页面等，不进 schema）。组件选型经查证收敛为**两列映射表**：桌面 Element Plus、移动 uni-app 内置组件（H5/APP壳/小程序同一运行时渲染器）。

**部署拓扑**：单一 Web 服务器同源共存——`/` 管理端、`/m/` uni H5 产物（生产入口与预览 iframe 一份产物两用）、`/api` 后端；注意点：路由 base 各配、localStorage/登录态需端上下文与 key 命名空间、SPA history fallback；小程序包不经此服务器，仅共后端。

**页面清单**：A1 客户端管理列表、A2 客户端设置抽屉（渠道/登录/授权）、A3 菜单管理端切换、A4 用户端身份 Tab、A5 发布目标端选择、B1 移动端运行态工作台（线框图见设计文档 §4）。**分期**：P0 建模+端树+角色挂端迁移+schema 审计 spike；P1 H5 端到端+脱敏字段策略+登录泛化；P2 APP 壳+小程序运行时壳+按端出制品。

## Alternatives Considered

### 方案 A：端 UI 由平台生成投放（schema → 各端渲染）
- **做法**：设计器产出 schema，各渠道由平台渲染器出成品；新增"自研端仅对接 API"的兼容路径
- **优点**：复用最强、单一资产；与平台现有 schema 驱动渲染管线一致
- **缺点**：移动原生体验受渲染器能力上限
- **为何未采用**：（未单独采用）纯 A 不覆盖 APP 推送/定位等原生诉求

### 方案 B：客户端全部自研，平台只提供 API/身份/流程能力
- **做法**：平台交付"能力"而非"App"，BFF/开放 API 契约为核心
- **优点**：端体验无上限，平台改造面最小
- **缺点**：交付物不含端，"新建端 = 配置"的目标落空，低代码价值丧失
- **为何未采用**：与需求"平台支持多端形态"背离；仅作混合路径保留

### 方案 C：混合——生成式渲染为主，原生核心模块经 JSBridge/出码补充（✅ 采用）
- **做法**：列表/表单/审批类页面由平台 schema 渲染进各容器；高频核心交互（司机接单、乘客地图）走原生壳 + JSBridge；出码线（已有 CodegenLab）保持独立用途
- **取舍**：接受"移动体验 = 渲染器模板集上限"，换取单一资产模型；出码不与预览混轨（避免同一 schema 两套执行模型的漂移）

### 组件集/小程序渲染子分叉（brainstorm 中实测查证后收敛）
- **Vant 4 一统**：✗ 查证——Vant4 仅 Web（操作 DOM），小程序不可用；`@vant/weapp` 是另一套 WXML 规范
- **uni-app/Taro 平台内预览**：✗ 查证——项目级编译管线，无法在管理端运行时挂载（Taro blended Vue3 有未解决 issue）
- **出码编译到 uni/Taro**：可行但渲染双轨漂移（预览=运行时 vs 产物=编译时）
- **✅ 采用**：uni-app Vue3 内置组件做移动渲染器（`dev:h5` 喂 H5 与 APP 壳、`dev:mp-weixin` 做"schema 解释器小程序"运行时壳）；映射表两列（EP/uni），三端统一运行时渲染单一模型

### 角色端隔离
- **N:N 白名单**（角色 × 允许端）：改动小；✗ 配错即越权，边界模糊
- **✅ 采用：角色挂单一端**（`sys_role.client_id`）：跨端人员 = 每端各授；错误语义"该端无角色"，不存在越权缝隙

### 客户端管理菜单位置
- **系统管理**：原提案；✗ 建端→发布→挂菜单闭环全在开发管理，跨目录来回跳
- **一级目录「端接入管理」**：✗ 新页面 <3 个不足以立目录
- **✅ 采用：开发管理**（V66"数据权限归位"同口径：按"哪拨人干什么事"归目录；path 与权限码命名空间不随目录走）

## Agreed Approach

方案 C（混合）+ 组件集采用 uni 内置单模型收敛。胜出原因：在"客户端/渠道不设限"的需求形状下，它是唯一同时满足 ①新建端不改平台代码（数据模型化）②三端单一渲染事实源（不出码双轨）③与平台既有资产（schema 驱动、sys_menu 挂接双闸、数据范围、V64 小程序绑定、V58/V66 菜单归位先例、codegen 线）增量兼容最小 的组合。

## Key Decisions

1. **Client/Channel 为数据实体**：`sys_client`、`sys_client_channel`；端集合开放扩展，WEB/H5/APP/MP 为渠道枚举能力
2. **存量菜单树整体归平台客户端**：迁移只加 `sys_menu.client_id` 回填；path/权限码/授权不动（V58 先例）
3. **端菜单形态**：WEB 三层树现状；移动端 = 底部 Tab(2~5) + 工作台宫格，同树两映射
4. **客户端管理归开发管理**（V66 口径）；菜单管理页加端作用域 Tab；不建新目录
5. **能力被引用不复制**：发布勾选目标端（A5）+ 端树挂接双闸；权限码跨端复用不加端前缀
6. **角色挂单一端**（`sys_role.client_id`，存量回填平台端）；登录链路校验端一致
7. **脱敏 = 数据范围 grant 字段策略**，服务端序列化层生效（详情/导出/API 同点封堵）
8. **schema 三层分界**：语义进 schema、布局进端覆盖层、交互骨架进渲染器框架
9. **移动渲染器 = uni-app Vue3 内置组件**；Vant 4 不单独引入；出码线独立用途不混轨
10. **部署 = 单服务器同源**：`/` 管理端、`/m/` uni H5（预览 iframe 与生产同产物）、`/api` 后端；小程序壳为唯一例外
11. **P0 前置 spike**：审计存量 schema 桌面渲染细节，分拣语义/表现字段
