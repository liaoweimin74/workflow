## Design Summary

在工作流平台中新增完整的消息通知模块，支持多渠道消息发送（站内信、短信、企业微信、微信小程序、APP）、消息模板管理、订阅/退订、管理端配置。消息来源涵盖工作流事件、系统消息、用户间通信、外部业务系统。Web 端提供铃铛+独立消息中心界面，支持多种跳转目标。

## Alternatives Considered

### 方案 A：单模块集中式
- **做法**：所有消息逻辑放在一个 `notification` 模块里，渠道适配器作为内部类
- **优点**：最简单，模块内自治，开发快
- **缺点**：渠道和核心耦合，新增渠道要改核心代码；业务模块依赖 notification 模块
- **为何未采用**：渠道耦合度高，未来扩展性差，不符合 Spring Modulith 模块化理念

### 方案 B：模块 + SPI 插件化渠道（选定）
- **做法**：核心模块 `notification` 负责消息模型、模板、存储、订阅；渠道作为 SPI 实现，业务模块通过 Spring Events 解耦
- **优点**：渠道完全解耦（新增渠道=新增适配器类）、业务层零感知（只发事件）、Spring Modulith 模块边界清晰、符合现有架构风格
- **缺点**：初始开发量略大于方案 A，需要设计好 SPI 接口契约
- **为何未采用**：此为选定方案

### 方案 C：事件驱动 + 独立消息服务（微服务化）
- **做法**：把消息服务完全拆成独立微服务，通过消息队列通信
- **优点**：最高扩展性，可独立部署和扩缩容
- **缺点**：运维复杂度大增，项目当前是单体架构（Spring Modulith），引入微服务过度设计
- **为何未采用**：项目当前阶段不适合微服务化，复杂度收益比不合理

## Agreed Approach

采用**方案 B（模块 + SPI 插件化渠道）**。核心模块 `notification` 管理消息全生命周期，渠道适配器通过 SPI 接口解耦，业务模块通过 Spring Events 发布消息事件，notification 模块监听并分发。发送策略为站内信同步写入 + 外部渠道异步发送（Spring Events + @Async），不引入 MQ。

## Key Decisions

1. **消息来源**：工作流事件、系统消息、用户间通信、外部业务系统（全覆盖）
2. **消息渠道**：Web 站内信、短信、企业微信、微信小程序、APP
3. **消息类型**：公共消息（广播）、私人消息（点对点）
4. **订阅模型**：混合模式——用户级全局类型开关 + 管理员级场景规则，紧急消息绕过订阅设置
5. **发送方式**：站内信同步 + 外部渠道异步（@Async + Spring Events，失败写重试表，定时任务 3 级退避重试）
6. **Web 端界面**：全局铃铛（未读数+最近消息下拉）+ 独立消息中心页面
7. **消息跳转**：支持流程实例页、外部链接、系统内任意页、移动端 deeplink（统一 linkTemplate）
8. **模板设计**：结构化 JSON 模板，按渠道 key 存储差异化内容，支持租户级覆盖
9. **前端架构**：所有新增代码放在 `src/modules/notification/` 独立目录下，为未来微前端做准备；复用 SearchTable、LookupPicker、DataPicker 等现有业务组件
10. **安全**：用户端只能操作自己的消息，管理端需 ADMIN 或 NOTIFICATION_MANAGER 角色，内部 API 限服务间调用，渠道配置 AES-256 加密
11. **实施分阶段**：P1 核心+站内信+消息中心（2-3周）→ P2 模板+订阅+管理端（2周）→ P3 渠道适配器（2周）→ P4 重试+监控（1周）
