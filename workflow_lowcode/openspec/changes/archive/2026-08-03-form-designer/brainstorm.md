## Design Summary

基于 PRD 3.2 表单设计器需求，开发工作流表单设计器。用户在浏览器中通过拖拽方式构建表单，产出的表单定义可被流程节点引用，运行时由表单引擎渲染。

本期覆盖 Layer 1（CRUD + schema + 运行时渲染）+ Layer 2（设计器 UI）+ Layer 3（字段权限最小版）。事件脚本（3.2.4）和可视化规则（3.2.5）推迟到下一期。

### 能力栈分层

```
Layer 4: 事件脚本 / 沙箱        ← 本期不做
         可视化规则引擎          ← 本期不做

Layer 3: 字段权限               ← 本期做（最小版：表单默认 + 节点覆盖）
         组件扩展机制            ← 本期不做

Layer 2: 拖拽设计器 UI          ← 本期做
         属性配置面板            ← 本期做
         schema 持久化           ← 本期做

Layer 1: 表单定义 CRUD API      ← 本期做
         表单 schema 数据模型    ← 本期做
         运行时渲染              ← 本期做（替换自研 FormBuilder）
```

### 组件范围（难度低 + 中）

| 分类 | 组件 |
|---|---|
| 核心-简单 | 单行文本、多行文本、数字输入、开关 |
| 核心-中等 | 下拉选择(单/多选)、单选、多选、日期、日期范围 |
| 核心-依赖 | 文件上传 |
| 扩展-组织 | 人员选择、部门选择（复用已有 ApproverPicker） |
| 扩展-数据 | 数据引用组件（自研数据源配置面板） |
| 扩展-容器 | 子表/表格、嵌套表单、分组容器、分割线 |

剔除组件（难度高，后续再做）：自动编号、富文本、评分、地址。

## Alternatives Considered

### 方案 A：Formily（@formily/element-plus + designable-vue）

- **做法**：采用阿里 Formily 生态，@formily/core 做 schema 引擎，@formily/element-plus 做 Element Plus 适配，designable-vue 做可视化设计器
- **优点**：
  - JSON Schema 标准化，schema 扩展性强
  - x-reactions 联动体系最强大（主动/被动/异步/effects 生命周期）
  - 阿里背书，生态大，社区活跃
  - 字段级权限可通过 schema 扩展实现
- **缺点**：
  - @formily/element-plus 自 2024-07 后停滞，近 1.5 年无更新
  - designable-vue 仅 8 star，社区 fork，非官方主力维护
  - 设计器 Vue 版本是二等公民，官方 Discussion 中有人反馈"找不到组件"
  - 数据源能力被官方放弃（Discussion #1629：不打算搞，直接上低代码）
  - 学习曲线陡峭，抽象层厚，定制成本高
- **为何未採用**：Vue 3 生态残缺是致命伤。联动能力再强，没有可用的设计器也白搭。@formily/element-plus 停滞意味着适配层风险不可控。

### 方案 B：form-create Pro 版（商业授权）

- **做法**：购买 form-create Pro 版（¥1880~¥4960 一次性买断），获得可视化规则编辑器、数据源配置 UI、字段权限 UI、90+ 组件
- **优点**：
  - 全部能力开箱即用，无需自研
  - 设计器成熟，Vue 3 + Element Plus 原生
  - 逻辑条件编辑器（AND/OR 条件组）直接对应 PRD 3.2.5
  - 数据源配置 UI 完整
  - 不限域名/项目数，一次性付费
- **缺点**：
  - 商业授权费用，需预算审批
  - 源码提供但许可证限制二次分发
  - 依赖商业团队维护，长期风险
- **为何未採用**：开源免费是项目约束。且本期范围（Layer 1+2+3）不需要 Pro 的高级能力，开源版 + 自研数据源面板已足够覆盖。

### 方案 C：VTJ.PRO（低代码平台）

- **做法**：采用 VTJ.PRO 作为低代码引擎，表单作为页面的一种形态
- **优点**：
  - 数据源能力最完整（项目级 API 管理 + 页面级数据源 + 数据转换 + 测试预览）
  - Vue 3 + Element Plus 深度整合
  - DSL 级 JSExpression/JSFunction 脚本能力强
  - 设计器成熟，支持源码与 DSL 双向转换
- **缺点**：
  - 定位是低代码页面搭建平台，不是表单设计器
  - 脚本能力面向页面组件（state/methods/watch/lifecycle），不是表单字段级联动
  - 用它做表单设计器是"杀鸡用牛刀"，引入完整低代码平台的复杂度
  - 表单字段级联动（显隐/计算/选项过滤）需要手写组件逻辑，失去配置驱动意义
- **为何未採用**：粒度错配。VTJ 的能力在页面级，而 PRD 3.2 需要的是表单字段级。未来做低代码平台时可作为页面引擎候选，但不适合当前表单设计器需求。

## Agreed Approach

### 方案 E：form-create 开源版 + 自研数据源面板

采用 form-create 开源版（MIT）作为表单引擎，自研数据源配置面板补齐设计器 UI 缺失。

**选型理由**：
1. 设计器开箱即用（@form-create/designer@3.x，2025-11 仍在迭代）
2. Vue 3 + Element Plus 原生支持
3. 运行时联动 API（control/update/on）可用，覆盖 PRD 3.2.4 基础场景
4. fetch 属性支持远程数据加载，自研 UI 面板产出 fetch 配置注入 schema
5. 30+ 内置组件覆盖本期全部需求
6. MIT 开源，无商业限制
7. 已有政务/OA/ERP/流程管理生产案例

**自研数据源面板**：form-create 的 `fetch` 属性是 JSON schema 的一部分，自研 UI 面板让用户配置 action/method/parse/headers，产出 `fetch` 对象注入 rule JSON。运行时由 form-create 引擎消费，不引入新的运行时依赖。

**未来扩展路线**：双引擎架构。表单引擎（form-create）和页面引擎（独立选型）通过 FormRenderer 物料组件桥接，各自独立演进。

## Key Decisions

| # | 决策 | 结论 |
|---|---|---|
| 1 | 本期范围 | Layer 1 + Layer 2 + Layer 3（字段权限最小版） |
| 2 | 组件范围 | 难度低 + 中（核心全部 + 文件上传 + 人员/部门 + 数据引用 + 子表/嵌套 + 分组/分割线） |
| 3 | 表单引擎 | form-create 开源版（MIT），设计器 @form-create/designer，渲染器 @form-create/element-ui |
| 4 | 表单复用 | 一个表单定义可被多个流程节点引用 |
| 5 | 版本管理 | 表单定义有版本管理（version 自增，已发布修改创建新版本） |
| 6 | 绑定粒度 | 支持流程级绑定（开始事件/整个流程）+ 节点级绑定（用户任务） |
| 7 | 表单实例存储 | 通用 JSON 表（wf_form_data），data_json 存完整表单数据 |
| 8 | 字段权限 | 混合模式：表单定义设默认权限（EDIT/VIEW/HIDDEN），流程节点 fieldPermissions 可覆盖 |
| 9 | 事件脚本 | 本期不做（PRD 3.2.4），下期补 |
| 10 | 可视化规则 | 本期不做（PRD 3.2.5），下期自研规则面板注入 control |
| 11 | 数据源 | 本期自研数据源配置面板，产出 fetch 配置注入 rule JSON |
| 12 | 运行时渲染 | form-create 替换自研 FormBuilder.vue |
| 13 | 未来低代码 | 双引擎路线，页面引擎独立选型，FormRenderer 物料桥接 |

## Open Questions

1. **表单版本管理细节**：已发布表单修改后是新版本还是覆盖？旧版本表单数据如何兼容？（倾向：新版本，旧数据保持关联旧版本 schema）
2. **表单绑定优先级**：节点级绑定是否覆盖流程级绑定？（倾向：是，节点级优先）
3. **组件扩展机制（PRD 3.2.2）**：本期是否需要开发者注册自定义组件的能力？（倾向：本期不做，先用内置组件）
