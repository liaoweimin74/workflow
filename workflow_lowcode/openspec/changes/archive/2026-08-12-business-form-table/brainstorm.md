## Design Summary

本变更新增**业务表单（底表）**的设计与渲染能力。当前系统已支持工作流表单（绑定流程节点、随任务渲染），但不支持独立于流程的"底表"——即表单定义发布后形成一张可查询、可约束、可增删改查的业务数据表。

核心设计：**统一设计器 + 宿主分层**。复用现有表单设计器（`@form-create/designer`）与渲染器（`FormRenderer.vue`），`wf_form_def` 增加 `type` 字段区分 WORKFLOW / BUSINESS；业务表单发布时通过**运行时受控 DDL** 创建物理表 `wf_biz_<formKey>`，字段经**列映射配置**转为结构化列；新增通用业务数据 CRUD API 与前端业务数据管理页。

v1 范围：纯底表 CRUD（设计 → 发布建表 → 行数据增删改查 + 分页查询）。data-picker 引用、流程沉淀写回、子表/嵌套表单、行级权限均留待 v2。

## Alternatives Considered

### 方案 A：统一设计器 + 物理表列映射（Agreed）
- **做法**：一个设计器、一份 schema（form-create `{rule, option}`）。`wf_form_def` 增加 `type`（WORKFLOW/BUSINESS）与 `column_config`（列映射）。发布 BUSINESS 表单时运行时 DDL 创建物理表 `wf_biz_<formKey>`（共享表 + tenant_id 列），字段经白名单校验后映射为结构化列；新增 `wf_biz_<formKey>` 行 CRUD API 与前端通用数据表格页。
- **優點**：
  - 设计器/渲染器/组件注册表/字段权限/校验 100% 复用，组件新增成本不翻倍
  - 物理表 SQL 可查、可约束（必填/唯一/索引）、可报表
  - 与现有系统逻辑隔离（共享表 + tenant_id）策略一致
  - `FormRenderer.vue` 已支持 `rule` 直传模式，前端复用无障碍
- **缺點**：
  - 动态 DDL 需要严格的列名/类型白名单校验防注入
  - 表单改版 = 表结构变更，需受控（只增列/改宽/改必填，禁删列）
- **為何未採用**：无。此为最终方案。

### 方案 B：统一设计器 + JSON 大字段表
- **做法**：复用 `wf_form_data` 模式，业务表单数据全部存 `data_json` 大字段，不建物理表。
- **優點**：实现最简、改版零成本、无 DDL 风险。
- **缺點**：按字段查询/排序/唯一约束/报表能力差，不满足"底表"（SQL 可查可约束）的核心诉求。
- **為何未採用**：底表的本质是结构化可查的数据集合，纯 JSON 无法支撑字段级查询、唯一性约束与报表联表。

### 方案 C：两个独立设计器
- **做法**：工作流表单与业务表单各自独立设计器、独立 schema 格式、独立渲染器。
- **優點**：设计能力可按场景深度定制（如业务表单专门的表格/筛选配置）。
- **缺點**：组件注册表、属性面板、渲染器全部双份维护，每新增一个组件成本 ×2；且工作流与业务表单在组件/布局/校验上需求高度重叠，重复建设。
- **為何未採用**：设计能力无本质差异，差异在宿主绑定层（流程节点 vs 数据源），统一设计器更符合成本与业界实践（钉钉/明道云等均为一套设计器多场景）。

### 方案 D：运行时受控 DDL vs Flyway 迁移脚本 vs 人工审核 DDL（建表机制取舍）
- **做法**：
  - D-1 运行时受控 DDL：发布表单时后端直接 CREATE/ALTER，白名单校验
  - D-2 Flyway 迁移脚本：发布时生成 V<版本>__form_<key>.sql，随部署生效
  - D-3 人工审核 DDL：发布生成草案，管理员确认后执行
- **優點/缺點**：
  - D-1：发布即生效、体验好；需严格校验防注入
  - D-2：安全可审计、回滚友好；需重启/编程式 migration，体验割裂
  - D-3：安全可控；多一步人工操作，体验差
- **為何未採用 D-2/D-3**：表单发布是高频自助操作，D-2 的部署耦合与 D-3 的人工审核与"设计器自助发布"体验冲突；D-1 配合白名单 + 版本表审计可满足安全与可追溯要求。

### 方案 E：共享表 + tenant_id vs 每租户独立建表（租户隔离取舍）
- **做法**：
  - E-1 共享表 + tenant_id：所有租户共用 `wf_biz_<formKey>`，行带 tenant_id
  - E-2 每租户独立建表：`wf_biz_<formKey>_<tenantId>`
- **優點/缺點**：
  - E-1：表数量可控、DDL 次数少、与现有逻辑隔离一致；唯一约束需 (tenant_id, 字段) 复合
  - E-2：隔离强、可独立索引；表数量随 租户×表单 爆炸、迁移管理复杂
- **為何未採用 E-2**：与系统既定的逻辑隔离策略（设计文档 §3.1）冲突，管理复杂度高，E-1 配合强制 tenant_id 过滤已满足隔离要求。

## Agreed Approach

采用**方案 A（统一设计器 + 物理表列映射）**，并叠加 D-1（运行时受控 DDL）与 E-1（共享表 + tenant_id）决策。理由：最大化复用现有表单资产（设计器/schema/渲染器），同时让业务表单具备真实"底表"能力（SQL 可查、可约束、可报表）。工作流表单零改动，业务表单仅新增宿主绑定层与数据层。

## Key Decisions

1. **统一设计器**：一个设计器 + 一份 form-create schema，不拆分独立设计器。差异收敛到"宿主绑定层"（流程节点绑定 vs 数据源绑定）。
2. **存储形态 = 物理表 + 列映射**：业务表单发布时创建 `wf_biz_<formKey>` 物理表；`column_config` 定义字段→列映射（类型/长度/必填/唯一/索引）。
3. **建表机制 = 运行时受控 DDL**：CREATE TABLE / ALTER TABLE 由后端在发布时执行；仅允许增列/改列宽/改必填/加索引，禁止删列与类型跨类变更；列名/类型/长度白名单校验防注入；结构变更随 `wf_form_def` 版本表审计。
4. **租户隔离 = 共享表 + tenant_id**：所有租户共用物理表，行级 tenant_id 强制过滤；唯一约束用 (tenant_id, 字段) 复合索引。
5. **v1 范围 = 纯底表 CRUD**：设计表单 → 发布建表 → 行数据增删改查 + 分页查询（筛选/排序）。新增通用 API `POST/GET/PUT/DELETE /api/v1/biz-data/{formKey}[/{id}]` 与前端业务数据管理页（动态列 + 复用 FormRenderer 编辑）。
6. **列类型映射规则**：单行文本/下拉/单选→VARCHAR；多选→VARCHAR(1024)（JSON/逗号分隔）；多行文本/富文本→TEXT；数字→INT/DECIMAL；日期→DATE；日期时间→DATETIME；日期范围→拆 start/end 两列；开关→TINYINT(1)；文件上传→JSON；子表/嵌套表单 v1 不支持（发布时提示）。
7. **类型字段扩展**：`wf_form_def` 新增 `type`（WORKFLOW/BUSINESS，默认 WORKFLOW 兼容旧数据）与 `column_config`（JSON，仅 BUSINESS 使用）。
8. **前端**：表单管理列表增加类型筛选；新增业务数据管理页 `/biz-data/:formKey`（通用表格 + 行编辑复用 FormRenderer rule 直传）；发布 BUSINESS 表单时生成列映射草案供确认调整。

## Open Questions

- v1 是否需要在发布时提供"列映射草案确认"交互（自动映射 vs 手动微调）？—— 设计默认为自动生成草案、允许手动覆盖类型/长度/唯一，具体交互在 implementation 阶段细化。
- 多选字段以逗号分隔还是 JSON 存储？—— 默认 JSON 数组字符串，v1 接受不可友好查询。
- 日期范围拆两列（start/end）的命名规则？—— 默认 `<key>_start` / `<key>_end`，列映射草案中展示。
