# 09 自定义开发

平台的「零代码圈」能覆盖标准增删改查、常规交互和常规审批流。当需求落到圈外——设计器组件族做不出来的交互、需要复用的手写资产、表单/流程事件里挂不进去的业务规则——就轮到本章：**前端两条路，后端一条路**，每条都给出完整示例与代码。

## 9.1 先判断：该不该写代码

| 需求形态 | 推荐做法 | 章节 |
| --- | --- | --- |
| 标准列表 + 表单 + 常规交互 | 页面设计器 + 数据源 + 动作总线（零代码） | [04 章](04-页面与数据源.md) |
| 复杂整页交互，且只在本项目用 | **前端方式一**：前端工程手写页面 | [本章 9.2](#9.2) |
| 复杂页面/组件，要跨项目复用或进设计器画布 | **前端方式二**：页面/组件物料 | [本章 9.3](#9.3) |
| 表单保存前后、流程节点里的业务规则 | 先试逻辑流（零代码编排）；写不了的算子沉淀成后端 Bean | [本章 9.4](#9.4) |

判断原则与 [07 章物料一节](07-模块与物料.md#7.2)一致：**硬写只会更痛的场景别写**——缺一个通用原子控件去提内置组件需求，强合规页面别把敏感逻辑打进物料。

## 9.2 前端方式一：在前端工程里手写页面

适用：整页交互设计器表达不了（多步向导、拖拽编排、虚拟滚动大表格……），且页面只在本项目使用。页面就是前端仓库里的一个普通 Vue 文件，随前端一起编译发布。

### 步骤 1：写页面组件

在 `frontend/src/views/` 下新建目录与组件，例如 `src/views/stock/StockBoardPage.vue`：

```vue
<script setup lang="ts">
import { ref, onMounted } from 'vue'
import http from '@/utils/http'

interface StockItem {
  id: number
  sku: string
  qty: number
}

const rows = ref<StockItem[]>([])
const loading = ref(false)
const keyword = ref('')

async function load() {
  loading.value = true
  try {
    // http 实例 baseURL 已是 /api，自动携带登录态，401 统一跳登录
    const res = await http.get('/stock/page', {
      params: { keyword: keyword.value, size: 50 },
    })
    rows.value = res.data?.content ?? []
  } finally {
    loading.value = false
  }
}

onMounted(load)
</script>

<template>
  <div class="p-4">
    <el-input v-model="keyword" placeholder="物料编码" class="w-60 mb-3" @keyup.enter="load" />
    <el-button type="primary" :loading="loading" @click="load">查询</el-button>

    <el-table v-loading="loading" :data="rows" border class="mt-3">
      <el-table-column prop="sku" label="物料编码" min-width="140" />
      <el-table-column prop="qty" label="库存量" width="120" />
    </el-table>
  </div>
</template>
```

要点：

- 取数统一走 `@/utils/http`（平台封装的 axios 实例），**不要**自己 new axios——租户头、token、错误提示都在里面；
- 权限判断用页面里已有的权限指令/工具（按钮级控制参考 [08 章](08-权限与菜单.md)），数据安全靠页面调用的后端接口鉴权兜底。

### 步骤 2：注册路由

平台路由是**静态声明**在 `frontend/src/router/index.ts` 里的。在 `AdminLayout` 的 `children` 数组中加一条（放在 `/404` 之前）：

```ts
{
  path: 'stock/board',
  name: 'StockBoard',
  component: () => import('@/views/stock/StockBoardPage.vue'),
  meta: { title: '库存看板' }
},
```

### 步骤 3：编译

```bash
cd frontend
pnpm dev      # 开发联调，http://localhost:3000
pnpm build    # 交付部署
```

### 步骤 4：挂菜单

**系统管理 → 菜单管理** 新建一条菜单（界面字段详解见 [08 章 8.1/8.2](08-权限与菜单.md#8.1)）：

| 字段 | 填写值 | 说明 |
| --- | --- | --- |
| 菜单类型 | 菜单 | |
| 菜单名称 | 库存看板 | 侧边栏显示名 |
| 路由路径 | `/stock/board` | 必须与步骤 2 的 `path` 完全一致（自动拼接在布局下） |
| 组件路径 | `stock/StockBoardPage` | 元数据记录（views 下相对路径），真正决定渲染的是路由声明 |
| 权限标识 | `stock:board:read` | 自定义，命名沿用 `模块:资源:动作` 约定 |

注意：静态路由本身不做菜单级拦截——入口可见性由菜单树控制，URL 直达由页面内接口的后端鉴权兜底，所以后端接口务必配好权限。

### 步骤 5：授权

**系统管理 → 角色管理** → 勾选该菜单 → 用户重新登录生效（操作见 [08 章 8.4](08-权限与菜单.md#8.4)）。

### 什么时候不用方式一

- 页面要给**其他项目**复用 → 方式二，导出 zip 整包带走；
- 不想改前端工程、不想跟着平台发版节奏走 → 方式二独立上传即生效。

## 9.3 前端方式二：页面/组件物料

物料 = 手写 Vue 打成 ESM 单文件包上传平台，之后像内置页面/组件一样使用，还能导出到别的项目导入。完整规范见 `material-scaffold/README.md`（随工程模板分发），这里给最短路径。

![物料管理](images/material-list.png)

### 步骤 1：下载工程模板

**开发管理 → 物料管理 → 下载工程模板**（需 `material:manage` 权限），解压得到脚手架工程。环境要求 Node ≥ 20.19（或 ≥ 22.12）+ pnpm。

### 步骤 2：改 manifest

页面型编辑 `material.json`：

```json
{
  "key": "stock-board",
  "name": "库存看板",
  "type": "PAGE",
  "sdkVersion": "1",
  "menu": { "title": "库存看板", "icon": "Grid" }
}
```

- `key` 全局唯一、上传后长期占用（软删也不释放），起个小写短横线名；
- `sdkVersion` 必须等于宿主配置（当前 `1`），不一致上传直接 400。

组件型（WIDGET）还要写 `meta` 数组声明属性面板——**必须是数组**（MySQL JSON 列会重排对象键序，数组是唯一能保序过库的形态），每项必有 `field` + `type`，且 `field` 要能对上组件的 props 名：

```json
{
  "key": "stat-card",
  "name": "指标卡",
  "type": "WIDGET",
  "sdkVersion": "1",
  "meta": [
    { "field": "title", "label": "标题",   "type": "text",   "default": "本月新增" },
    { "field": "value", "label": "指标值", "type": "number", "default": 128 },
    { "field": "trend", "label": "趋势",   "type": "select", "default": "up",
      "options": [ { "label": "上升", "value": "up" }, { "label": "下降", "value": "down" } ] }
  ]
}
```

### 步骤 3：写组件，只用三个依赖

```vue
<script setup>
import { ref, onMounted } from 'vue'
import { http, auth, navigate } from '@platform/sdk'

const rows = ref([])
const canExport = auth.hasPermission('stock:export')

onMounted(async () => {
  const res = await http.get('/stock', { params: { size: 50 } }) // baseURL 已是 /api
  rows.value = res.data?.content ?? []
})
</script>
```

**硬性规范**（违反必被拒或白屏，构建脚本会拦）：

- 只能 import `vue` / `element-plus` / `@platform/sdk` 三个裸模块名，**任何第三方库、子路径导入都不行**——多打进去一个 Vue 实例就是「看着渲染了但点了没反应」；
- 只用 ESM 语法（无 `require` / `module.exports`）；
- 样式类名带物料前缀，颜色读 `var(--el-*)`——注入的 `<style>` 是全局生效的；
- bundle ≤ 5MB。

### 步骤 4：构建并上传

```bash
pnpm install
pnpm build          # 页面型 → dist/page/bundle.js + manifest.json
pnpm build:widget   # 组件型 → dist/widget/bundle.js + manifest.json
```

物料管理 → **上传物料** → 分别选 `dist/*/` 里的 `bundle.js` 与 `manifest.json`。同 key 重复上传 = 版本 +1 覆盖，**平台不存版本历史**，回滚只能重传旧包。

### 步骤 5：挂菜单（页面物料）

物料行操作里点**挂到菜单**，按约定自动创建：路由路径 `/material/<key>`、组件路径 `material:<key>`（固定不可改）。菜单要启用、角色要授权，入口才可见。

组件物料则不需要挂菜单：上传后进页面设计器左侧「自定义物料」分组，**点一下**即入画布，属性面板按 `meta` 顺序生成控件。

### 步骤 6：跨项目复用

物料管理勾选 → **导出选中** 得到 zip → 另一项目 **导入物料包** → 看预检表（全新 / 已存在 / 不可导）→ 冲突条目逐条选覆盖或跳过（**默认跳过**）。导入即启用，但菜单要在目标项目**单独挂**——物料不携带菜单结构。

## 9.4 后端开发：在表单与流程事件里挂 Java 逻辑

表单事件、流程节点里需要业务规则（库存校验、单号生成、扣减库存……）时，优先用逻辑流零代码编排（[06 章](06-逻辑编排.md)）；编排不了的，按场景从三个扩展点里选：

| 扩展点 | 挂在哪 | 典型用途 |
| --- | --- | --- |
| `BizDataHandler` | **自动接线**——实现接口即生效，平台内零配置 | 业务表单增删改查的校验、回写、行级过滤、接管查询 |
| `@BackendLogicBean` | 逻辑流 Bean 方法节点、Groovy 脚本 `beans.<bean>.<method>()` | 表单事件、流程里复用的业务函数 |
| 服务任务 `java` 类型 | 流程中直接调任意 Spring Bean | 节点级后端动作 |
| 服务任务 `logicflow` 类型 | 流程中调逻辑流 | 流程编排逻辑流 |
| `AssigneeResolver` | 流程节点「自定义选人函数」 | 按业务规则动态选人 |
| `FlowableEventListener` | 引擎全局事件（[见 9.4.6](#9.4.6)） | 任意流程的生命周期钩子（审计、提醒、外部同步） |

`BizDataHandler` 与表单事件绑定逻辑流是**同一条业务规则的两条路**：逻辑流在平台里配置、改了即生效但编排能力有限；Handler 是纯代码、能力不受限但要随服务编译部署。同一表单同一触发点别叠加两套，避免校验重复执行。

### 9.4.1 业务表单钩子：实现 BizDataHandler（不挂逻辑流、不写 Bean 白名单）

适用：规则与**某张业务表单的增删改查**强绑定。写一个类即可——实现 `BizDataHandler` 接口并注册为 Spring Bean，平台按 `getFormKey()` 自动接线，`BizDataService` 在 CRUD 各环节自动调用对应钩子；钩子里抛 `BusinessException` 即拒绝当前操作（配合事务回滚）。

| 钩子 | 时机 | 抛 BusinessException 的效果 |
| --- | --- | --- |
| `beforeCreate(data)` | 新增前 | 拒绝创建（400） |
| `afterCreate(created)` | 新增成功后 | 同事务内异常回滚主操作 |
| `beforeUpdate(data, existing)` | 更新前 | 拒绝更新 |
| `beforeDelete(existing)` | 删除前 | 拒绝删除 |

**例 1：校验 + 回写**（平台示例 `LeaveBillHandler`，请假超 5 天必须填理由，创建后置草稿状态）：

```java
@Component
public class LeaveBillHandler implements BizDataHandler {

    private static final String FORM_KEY = "leave_bill";

    private final BizDataSupport support;

    public LeaveBillHandler(BizDataSupport support) {
        this.support = support;
    }

    @Override
    public String getFormKey() { return FORM_KEY; }

    @Override
    public void beforeCreate(Map<String, Object> data) {
        Object daysObj = data.get("days");
        int days = daysObj instanceof Number n ? n.intValue() : 0;
        if (days > 5) {
            Object reason = data.get("reason");
            if (reason == null || String.valueOf(reason).isBlank()) {
                throw new BusinessException(400, "请假超过 5 天必须填写理由");
            }
        }
    }

    @Override
    public void afterCreate(BizDataVO created) {
        // afterCreate 内直接改 VO 不落库；回写走 support.updateGeneric（带 version 乐观锁）
        support.updateGeneric(FORM_KEY, created.getId(), Map.of("status", "草稿"), created.getVersion());
    }
}
```

**例 2：接管查询——行级过滤 + 补充计算列**（平台示例 `EmpProfileHandler`）。这也是 [8.5 数据范围](08-权限与菜单.md#8.5)里「只看本部门数据」的一种代码级落地：

```java
@Component
public class EmpProfileHandler implements BizDataHandler {

    private final BizDataSupport support;

    public EmpProfileHandler(BizDataSupport support) {
        this.support = support;
    }

    @Override
    public String getFormKey() { return "emp_profile"; }

    @Override
    public boolean overridesQuery() { return true; }   // 声明接管查询，通用实现不再执行

    @Override
    public BizDataPageVO query(BizDataQueryRequest req) {
        BizDataPageVO page = support.queryGeneric("emp_profile", req);
        Long orgId = currentUserOrgId();
        List<BizDataVO> records = new ArrayList<>();
        for (BizDataVO vo : page.getRecords()) {
            if (orgId != null && !orgIdMatches(vo, orgId)) {
                continue;                              // 非本部门行直接滤掉
            }
            records.add(decorateWorkingDays(vo));      // 补充「在职天数」计算列
        }
        return new BizDataPageVO(records, records.size(), page.getPage(), page.getSize());
    }
}
```

**覆盖模式**：除查询外，`overridesCreate()` / `overridesUpdate()` / `overridesDelete()` 返回 `true` 时对应操作被 Handler **完整接管**（须实现 `create(Map)` / `update(id, data, version)` / `delete(id)`，通用实现与钩子链都不再执行），适合存储结构特殊、需要连表写多表的表单。

**要点**：

- 平台提供了通用实现工具 `BizDataSupport`（`createGeneric` / `queryGeneric` / `updateGeneric`（带 version 乐观锁）/ `deleteGeneric` / 子表行操作），接管时可以复用它做通用部分，只写差异逻辑；
- `formKey` 对应业务表 `wf_biz_<formKey>`，一个 formKey 一个 Handler；
- 两个开箱示例在 `com.workflow.example` 包（`LeaveBillHandler`、`EmpProfileHandler`），接入前建议先读。

### 9.4.2 写一个 @BackendLogicBean

平台内已有范例 `ScriptToolkitBean`（字典翻译、UUID 等只读工具）。照它的样子，在你的业务包里写：

```java
@BackendLogicBean
@Component("stockBean")
public class StockLogicBean {

    private final StockService stockService;

    public StockLogicBean(StockService stockService) {
        this.stockService = stockService;
    }

    /**
     * 出库前校验：库存不足抛异常，前端「保存/提交」动作被拒绝并提示。
     * rowData 即表单当前行数据。
     */
    public void checkStock(Map<String, Object> rowData) {
        String sku = (String) rowData.get("sku");
        int qty = ((Number) rowData.get("qty")).intValue();
        if (!stockService.enough(sku, qty)) {
            throw new IllegalArgumentException("库存不足：" + sku);
        }
    }

    /** 出库通过后扣减库存并写流水（后触发点调用）。 */
    public void deduct(Map<String, Object> rowData) {
        String sku = (String) rowData.get("sku");
        int qty = ((Number) rowData.get("qty")).intValue();
        stockService.deduct(sku, qty);
    }
}
```

规则：

- 类上标 `@BackendLogicBean` 并注册为 Spring Bean（`@Component("bean名")`）；
- **public 方法自动进入白名单**，出现在逻辑流「Bean 方法」节点下拉与 Groovy 补全里；非 public、参数个数不符会被注册器拦截；
- 白名单语义是安全边界：脚本/逻辑流**只能**调到白名单方法，别把危险操作放进来。

### 9.4.3 绑定到表单事件

入口：表单/页面表单组件 → **事件 Tab**（界面详解见 [04 章 4.8.4](04-页面与数据源.md#4.8.4)）→ 为「保存」等事件绑定逻辑流，选**前/后触发点**：

- **前触发**：动作执行前调用，逻辑流抛异常 = 拒绝本次操作——把 `checkStock` 挂在这里；
- **后触发**：动作成功后调用——把 `deduct` 挂在这里。

逻辑流里加一个 **Bean 方法节点**，下拉选择 `stockBean → checkStock`；或用 Groovy 脚本节点写：

```groovy
beans.stockBean.checkStock(row)
```

`beans.` 有代码补全（[06 章 6.3](06-逻辑编排.md#6.3)），候选就是全部白名单方法。

### 9.4.4 挂到工作流：服务任务

流程设计器里拖**服务任务**节点，四种类型按需选（[05 章 5.7](05-流程编排.md#5.7)）：

| 类型 | 配置 | 引擎行为 |
| --- | --- | --- |
| `java` | bean 名 `stockBean` + 方法名 `deduct` | 按 UEL `${stockBean.deduct(execution)}` 调用，**任意 Spring Bean** 可调（不要求 @BackendLogicBean） |
| `logicflow` | flowKey | 交给逻辑流执行（部署时校验 flowKey 存在） |
| `expression` | UEL 表达式 | `${body}` 求值 |
| `http` | — | **无内置同步委托**，只支持异步/重试，同步 HTTP 调用请在 Bean 里写 |

下图是选中服务任务节点后的属性面板（示例：调用逻辑流 `e2e_demo_ok`）：

![服务任务属性面板：服务类型 + 逻辑流入出参映射 + 失败策略](images/service-task-logicflow.png)

- **服务类型**：下拉四选一（Java 服务调用 / 表达式 / 调用逻辑流 / HTTP 调用）；
- 选「调用逻辑流」后出现**逻辑流**下拉（只列已发布的流）与**入参映射 / 出参映射**：每行左侧填**流程变量名**、右侧填**逻辑流变量名**，箭头表示方向；
- **失败策略**：失败阻断（流程停住）/ 失败继续（忽略本次失败往下走）；
- **执行与重试**：异步执行开关与失败重试次数，配合边界事件做补偿见 [05 章 5.5](05-流程编排.md#5.5)。

#### 变量怎么取、怎么写

先记住一句话：**发起 / 审批提交的表单字段会平铺写入流程变量**。所以服务任务里能拿到的变量 = 表单字段 + 平台内置变量（`approved`、`rejected`、`recalled`、会签的 `voteApprovedWeight` 等）+ 你自己写回的变量。

| 类型 | 取变量 | 写回变量 |
| --- | --- | --- |
| `java` | 方法签名拿 `DelegateExecution`，`execution.getVariable("days")` | `execution.setVariable("deductAmount", 500)` |
| `expression` | UEL 里直接写变量名，如 `${days > 5}` | 表达式本身不落变量；要写回用 `java` 或 Groovy |
| `logicflow` | 节点配置 **入参映射**：`source` 填流程变量名 → `target` 填逻辑流输入变量名 | 逻辑流的输出变量经 **出参映射** 写回：`source` 填输出变量名 → `target` 填流程变量名 |

逻辑流内部三种节点（[06 章 6.3](06-逻辑编排.md#6.3)）取的是逻辑流自己的变量（含入参映射进来的流程变量）：

| 节点 | 取变量 | 返回值 |
| --- | --- | --- |
| HTTP | URL / body 里写 `{{变量名}}` 占位符，如 `?sku={{sku}}&qty={{qty}}` | — |
| Bean 方法 | 参数映射里逐个选变量 | — |
| Groovy | 变量**直接就是脚本里的名字**：`if (days > 5) {...}`；调后端 Bean 用 `beans.xxx.method(...)` | 脚本**最后一个表达式**即返回值，可经出参映射写回流程变量 |

串起来的例子：请假流程 → Groovy 节点直接算 `days * 100` → 返回值经出参映射写回流程变量 `deductAmount` → 后面的排他网关条件写 `${deductAmount > 500}` 分流。

`java` 类型写回的完整示例：

```java
/** 计算请假扣款：days 为发起表单字段，deductAmount 写回后供网关条件使用。 */
public void calcDeduct(DelegateExecution execution) {
    int days = (Integer) execution.getVariable("days");
    execution.setVariable("deductAmount", days * 100);
}
```

> 引擎另支持节点级「后端逻辑项」（进入/完成节点时触发 http / bean / script，带 `resultVar` 写回），当前设计器暂未提供配置入口，**【规划中】**——现阶段在节点上挂逻辑请用服务任务。

失败处理：给服务任务挂**边界事件**（[05 章 5.5](05-流程编排.md#5.5)），按错误码分流到补偿或终止路径；`FAIL_FLOW` / `IGNORE_CONTINUE` 决定失败即停还是忽略续跑。

### 9.4.5 自定义选人：实现 AssigneeResolver

内置的选人方式（指定用户/角色/发起人上级等）覆盖不了业务规则时——「按设备找管理员」「找发起人部门负责人」「按单据金额分级找主管」——就写一个自定义选人函数。

**接入方式**：实现 `AssigneeResolver` 接口并注册为 Spring Bean，即自动纳入注册表。之后在流程设计器选中审批/办理节点 → **办理人/审批人设置 → 自定义选人函数**，下拉里就会出现你的函数（显示 `displayName()`），选中后面板按 `paramDefs()` 渲染参数表单，配置值随节点持久化。

#### 例 1：从流程变量直接取人

最简单的场景：发起表单上有字段直接存用户 ID（如「指定审核人」）。发起时表单字段会**平铺写入流程变量**，选人函数直接读变量即可：

```java
@Component
public class AssignerResolver implements AssigneeResolver {

    @Override
    public String name() { return "form_assigner"; }

    @Override
    public String displayName() { return "表单指定审核人"; }

    @Override
    public List<AssigneeParamDef> paramDefs() {
        return List.of(new AssigneeParamDef(
                "varName", "表单字段名", "string", true,
                "如：reviewer_id", "reviewer_id", null,
                "存放审核人用户 ID 的表单字段名"));
    }

    @Override
    public List<String> resolve(AssigneeResolveContext ctx, Map<String, Object> params) {
        String varName = String.valueOf(params.getOrDefault("varName", "reviewer_id"));
        Object userId = ctx.variables().get(varName);
        return userId == null ? List.of() : List.of(String.valueOf(userId));
    }
}
```

参数化 `varName` 的好处：同一个函数，A 节点配 `reviewer_id`、B 节点配 `safety_officer_id`，不用写两个类。

#### 例 2：按组织架构选人（部门负责人）

选人逻辑要查库时，注入你的业务 Service 在 `resolve` 里同步查询。例如向上找 N 级部门的负责人：

```java
@Component
public class DeptLeaderResolver implements AssigneeResolver {

    private final OrgService orgService;

    public DeptLeaderResolver(OrgService orgService) {
        this.orgService = orgService;
    }

    @Override
    public String name() { return "dept_leader"; }

    @Override
    public String displayName() { return "部门负责人"; }

    @Override
    public String description() { return "按发起人所在部门向上找 N 级负责人"; }

    @Override
    public List<AssigneeParamDef> paramDefs() {
        return List.of(new AssigneeParamDef(
                "level", "向上几级", "number", false,
                "从 1 开始", 1, null,
                "1=本部门负责人，2=上级部门负责人，以此类推"));
    }

    @Override
    public List<String> resolve(AssigneeResolveContext ctx, Map<String, Object> params) {
        int level = params.get("level") instanceof Number n ? n.intValue() : 1;
        // ctx.initiator() 是发起人用户 ID
        return orgService.leaderOfDept(ctx.initiator(), level);
    }
}
```

#### 例 3：按业务数据选人

典型如设备报修：办理人应该是**这台设备的管理员**，而不是某个固定角色。思路是从流程变量里拿业务主键，再查业务数据：

```java
@Component
public class EquipmentOwnerResolver implements AssigneeResolver {

    private final EquipmentService equipmentService;

    public EquipmentOwnerResolver(EquipmentService equipmentService) {
        this.equipmentService = equipmentService;
    }

    @Override
    public String name() { return "equipment_owner"; }

    @Override
    public String displayName() { return "设备管理员"; }

    @Override
    public List<AssigneeParamDef> paramDefs() {
        return List.of(new AssigneeParamDef(
                "idVar", "设备 ID 变量名", "string", true,
                "如：equipment_id", "equipment_id", null,
                "存放设备 ID 的表单字段名"));
    }

    @Override
    public List<String> resolve(AssigneeResolveContext ctx, Map<String, Object> params) {
        String idVar = String.valueOf(params.getOrDefault("idVar", "equipment_id"));
        Object equipmentId = ctx.variables().get(idVar);
        if (equipmentId == null) {
            return List.of();
        }
        return equipmentService.findManagerIds(String.valueOf(equipmentId));
    }
}
```

同一模式适用于：按单据归属门店找店长、按合同找法务对接人等——**凡是「人由数据决定」的审批，都走这条扩展点**，比在流程里写死名单可维护得多。

#### 规则与约束

| 项 | 说明 |
| --- | --- |
| 注册名唯一 | `name()` 全局唯一（对应节点的 resolver 配置值），`displayName()` 也全局唯一，重复时**启动失败** |
| 必须同步返回 | `resolve` 要**同步**返回用户 ID 列表；查库可以，但不能改成异步回调 |
| 空列表语义 | 返回空列表、抛异常，都按「解析不出」处理，落节点的**「找不到办理人」策略**（[05 章 5.3](05-流程编排.md#5.3)） |
| 变量是快照 | `ctx.variables()` 为流程变量快照，修改无效；发起表单字段已平铺在内 |
| 选人返回的是**用户 ID** | 不是用户名、不是工号，与平台用户表的 ID 对齐 |
| 参数类型 | `paramDefs` 的 type 支持 `string` / `number` / `boolean` / `select`（select 配 `options`，每项 `new AssigneeParamDef.Option(label, value)`） |

平台自带三个开箱样例（`SampleAssigneeResolvers`：表单变量取人 / 固定用户组 / 顺序轮选），覆盖三种参数类型，接入前建议先读它们的写法。

### 9.4.6 全局监听器扩展：实现 FlowableEventListener

服务任务是**挂在某个流程节点上**的；如果需要的是**任意流程都生效**的全局生命周期钩子——每次任务创建发提醒、流程实例结束时同步外部系统、审批行为留审计——用 Flowable 的全局事件监听器：实现接口注册为 Spring Bean 即自动注册进引擎，无需任何平台配置。

```java
import org.flowable.common.engine.api.delegate.event.FlowableEngineEntityEvent;
import org.flowable.common.engine.api.delegate.event.FlowableEngineEventType;
import org.flowable.common.engine.api.delegate.event.FlowableEvent;
import org.flowable.common.engine.api.delegate.event.FlowableEventListener;

@Component
public class ProcessAuditListener implements FlowableEventListener {

    @Override
    public void onEvent(FlowableEvent event) {
        try {
            if (FlowableEngineEventType.PROCESS_COMPLETED.equals(event.getType())
                    && event instanceof FlowableEngineEntityEvent entityEvent) {
                String processInstanceId = String.valueOf(entityEvent.getEntity().getId());
                auditService.recordFinished(processInstanceId);
            }
        } catch (Exception e) {
            // 先在监听器内部兜住，别把异常抛回引擎
        }
    }

    @Override
    public boolean isFailOnException() {
        return false;   // 审计失败不阻断流程
    }
}
```

全局监听器会收到**所有流程、所有类型**的引擎事件，按 `event.getType()` 自行过滤。常用事件类型：

| 类别 | 事件 |
| --- | --- |
| 任务 | `TASK_CREATED` / `TASK_ASSIGNED` / `TASK_COMPLETED` |
| 流程实例 | `PROCESS_STARTED` / `PROCESS_COMPLETED` / `PROCESS_CANCELLED` |
| 活动 | `ACTIVITY_STARTED` / `ACTIVITY_COMPLETED` / `ACTIVITY_CANCELLED` |
| 作业 | `JOB_EXECUTION_FAILURE` 等（异步作业失败重试） |

规则与约束：

| 项 | 说明 |
| --- | --- |
| 注册方式 | 实现 `FlowableEventListener` + `@Component`，自动注册；派发顺序在平台监听器（节点后端逻辑）之后 |
| 事件负载 | `FlowableEvent.getType()` 取类型；实体事件可 `instanceof FlowableEngineEntityEvent` 拿到实体（任务、执行实例等）；要读流程变量须经 RuntimeService 按 processInstanceId 查 |
| `isFailOnException` | `true`＝异常中断当前引擎命令并回滚（业务校验类用，慎用）；`false`＝引擎记日志后继续（通知/审计类）。无论哪种，建议 `onEvent` 内部先 try-catch |
| 性能 | 监听器处在引擎每条命令的派发路径上，逻辑要轻；HTTP 等慢调用不要同步做，或做好超时与降级 |
| 与服务任务分工 | 某个节点上的业务动作 → 服务任务 `java`（[9.4.4](#9.4.4)）；跨流程全局生效的钩子 → 本节 |

## 9.6 常见问题

**Q：方式一改了代码要重新部署吗？** 要。路由与页面都随前端工程编译，`pnpm build` 后重新发布前端；菜单/授权数据在库里，不用动。

**Q：物料上传后白屏/报错块？** 九成是依赖被打进包了：控制台看第一个 `import()` 失败的模块名，按 [9.3 步骤 3](#9.3) 的规范删掉第三方 import。构建脚本能拦住大部分，别绕开它手工拼包。

**Q：逻辑流 Bean 方法节点里找不到我的方法？** 检查三点：类标了 `@BackendLogicBean`、注册成了 Spring Bean（服务在跑）、方法是 public。改完后端要重启服务才重新扫描。

**Q：写了 BizDataHandler 但没生效？** 同样查三点：`getFormKey()` 返回值与业务表单的 formKey 完全一致（对应表 `wf_biz_<formKey>`）、类注册成了 Spring Bean 且在扫描包路径下、后端已重新编译部署——钩子是纯代码接线，平台界面里没有任何配置项可核对。

**Q：服务任务里能发 HTTP 请求吗？** `http` 类型没有内置同步委托（只有异步/重试语义）。同步调用请在自己的 Bean 里用 HTTP 客户端写，再按 [9.4.4](#9.4.4) 以 `java` 类型挂进流程。

**Q：前触发校验拒绝了操作，用户看到什么？** 异常消息会作为操作失败提示返回前端——所以 `checkStock` 里抛的异常要写人话（「库存不足：SKU-001」），别抛裸 NPE。
