## Context

工作流平台当前无任何消息通知能力。PRD 3.7 仅设计了站内信+外部渠道预留接口，但完全未实现。本设计将构建一个完整的消息通知平台，支持多渠道、多来源、可订阅的消息系统。

**当前状态**：
- 后端：Java 21 + Spring Boot 4 + Spring Modulith + Flowable 8
- 前端：Vue 3 + Element Plus + Vite
- 数据库：MySQL + Flyway 迁移
- 模块结构：`engine`（流程引擎）、`system`（系统管理）、`api`（REST层）
- 无任何通知相关代码

**约束**：
- 必须符合 Spring Modulith 模块化架构
- 前端新增代码放在独立目录 `src/modules/notification/`，为未来微前端做准备
- 复用现有业务组件（SearchTable、LookupPicker、DataPicker 等）
- 不引入额外中间件（MQ），使用 Spring Events + @Async

## Goals / Non-Goals

**Goals:**
- 构建可扩展的消息通知核心模块，支持站内信、短信、企业微信、微信小程序、APP 五种渠道
- 支持四种消息来源：工作流事件、系统消息、用户间通信、外部业务系统
- 提供 Web 端完整的消息处理界面（铃铛 + 消息中心）
- 管理端提供模板、渠道、订阅规则、发送记录的配置能力
- 渠道适配器 SPI 化，新增渠道只需实现接口

**Non-Goals:**
- 不实现移动端（APP/小程序）前端，仅提供 API 和 deeplink 支持
- 不引入消息队列（Kafka/RabbitMQ），异步通过 Spring Events + @Async 实现
- 不实现邮件渠道（PRD 后续阶段再考虑）
- 不做场景级细粒度订阅（用户端仅类型级开关，场景级由管理员配置）

## Decisions

### D1: 模块化架构 — 方案 B（SPI 插件化渠道）
**选择**：核心模块 + SPI 渠道适配器，业务通过 Spring Events 解耦
**理由**：
- 符合 Spring Modulith 模块化理念，与现有 engine/system 模块风格一致
- 渠道完全解耦，新增渠道 = 新增一个适配器实现类
- 业务层零感知，只发布事件不 import 任何通知类
**替代方案**：单模块集中式（耦合高）、微服务化（过度设计）

### D2: 发送策略 — 站内信同步 + 外部渠道异步
**选择**：站内信同步写入 DB，外部渠道通过 @Async 异步发送
**理由**：
- 站内信同步保证用户即时可见，失败概率极低
- 外部渠道调用可能慢或超时，异步不阻塞业务流程
- 失败写入重试表，定时任务 3 级退避重试（1min/5min/30min，最多3次）
**替代方案**：全同步（阻塞业务）、全异步（站内信延迟可见）、引入 MQ（复杂度高）

### D3: 模板设计 — 结构化 JSON 模板
**选择**：JSON 格式存储，按渠道 key 存储差异化内容
**理由**：
- 支持多渠道差异化渲染（短信纯文本、企微富文本、小程序带 path）
- `linkTemplate` 统一管理跳转逻辑，前端根据 type 决定路由方式
- `variables` 声明模板变量，发送时校验必填参数
- 支持租户级模板覆盖

### D4: 订阅模型 — 混合模式
**选择**：用户级全局类型开关 + 管理员级场景规则
**理由**：
- 用户端简单直观（按消息类型开关），不需要复杂配置
- 管理员可通过场景规则精细控制（如财务流程催办强制发短信）
- 紧急消息（URGENT 优先级）绕过所有订阅设置
- 系统公告类消息不可退订

### D5: 前端模块化 — 独立目录 + 复用组件
**选择**：所有新增代码放在 `src/modules/notification/`，复用 SearchTable、LookupPicker 等
**理由**：
- 为未来微前端（Module Federation）做准备
- 复用现有成熟组件，减少开发量，保持 UI 一致性
- 唯一需修改其他模块的地方：全局铃铛组件在 layouts 中引入

### D6: 消息跳转 — 统一 linkTemplate
**选择**：消息携带通用 link 结构（type + url + params + deeplink）
**理由**：
- 统一管理跳转逻辑，支持四种目标：流程实例页、外部链接、系统内任意页、移动端 deeplink
- 前端根据 link.type 决定路由方式（router.push / window.open / location.href）

## Risks / Trade-offs

| 风险 | 缓解措施 |
|---|---|
| 异步发送失败导致消息丢失 | 重试表 + 定时任务兜底 + 管理端手动重发 |
| Spring Events 在进程崩溃时丢失事件 | 站内信同步写入已保证，外部渠道可通过重试表恢复 |
| 多租户模板管理复杂度 | 第一期仅超级管理员管理模板，租户级覆盖后续迭代 |
| 渠道适配器 API 变更 | SPI 接口稳定后冻结版本，变更通过新版本接口实现 |
| 前端模块拆分后路由注册 | 通过 router/index.ts 统一注册，模块暴露自己的路由配置 |
