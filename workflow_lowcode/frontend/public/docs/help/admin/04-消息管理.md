# 04 消息管理

平台的消息链路是一条流水线，理解顺序再操作：

```
事件定义（发生了什么） → 订阅规则（推给谁、走哪个渠道） → 模板（渲染成什么样） → 渠道（怎么送达） → 发送记录（结果与重发）
```

## 4.1 事件管理

系统内可触发通知的业务事件清单（事件编码、名称、参数）。新事件由开发侧在代码中注册后出现在这里，管理员一般只查看与核对，不在此新建。

## 4.2 订阅规则

把「事件」与「接收人 + 渠道」连起来的规则：

1. 选事件 → 设定接收人范围（指定用户/角色/成员组等，按界面选项）→ 选择下发渠道（可多选）；
2. 一条规则对应一种「事件 → 渠道」组合，需要「同事件既发站内信又发短信」就建两条；
3. 规则启停即时生效，停用期间积压的事件不会补发。

## 4.3 模板管理

通知文案的模板，变量占位渲染事件参数：

- 新建模板：选关联事件、标题模板、内容模板，占位符用事件参数（模板编辑界面会给出可用变量）；
- 内容支持富文本/多行文本等形态（按编辑器实际支持）；
- 改模板立即对后续发送生效，已发送的历史记录保持当时文案。

## 4.4 渠道配置

各送达渠道的接入参数，按渠道类型提供表单：

| 渠道 | 是否需要配置 | 要点 |
| --- | --- | --- |
| 站内信（IN_APP） | 无需参数 | 默认可用；消息在「消息中心」查看 |
| APP | 无需参数 | App 端推送 |
| 短信（SMS） | 需要 | 短信服务参数（按配置表单填写） |
| 企业微信 | 需要 | 应用与回调参数 |
| 小程序 | 需要 | 小程序订阅消息参数 |

- 配置保存前可用测试发送验证（按界面提供的测试入口）；
- 渠道参数错误通常表现为发送记录里整批失败，先查配置再查订阅。

## 4.5 发送记录

每一次通知的执行结果：状态（成功/失败）、渠道、接收人、时间。

- 失败记录支持**重发**（需「发送记录重发」按钮权限）；整批失败先修渠道配置，再批量重发；
- 发送记录同时是排查「用户说没收到」的第一现场：没记录 = 触发/订阅没生效；有记录但失败 = 渠道问题。

## 4.6 公告管理

面向全员/指定范围的系统公告，在首页或消息中心展示（按公告设置）。发布前核对：范围、起止时间、内容富文本是否完整。

## 4.7 消息中心

管理员自己（及全体用户）的个人消息收件箱：已读/未读、按渠道/时间筛选。排查「通知到了没」时让用户先来这里看站内信。
