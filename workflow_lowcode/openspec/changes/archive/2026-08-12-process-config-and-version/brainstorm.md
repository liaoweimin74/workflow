## Design Summary

针对工作流平台现有配置与版本体系的四个问题（流程级 vs 节点级配置、转签/转派/委派语义、部署变化检测、历史版本查看）进行方案探讨，收敛为"配置层级模型 + 版本与快照体系"两个设计支柱。

**问题 1（配置层级）**：节点级 `operations`（5 个操作权限位）是运行时唯一依据；流程级 `__PROCESS__` 配置中的 `allowAddSigner` / `allowDelegate` 是残留死代码（已标 `@deprecated`，后端无消费方）。收敛方案：操作权限类配置（驳回/加签/转办/委派）提升为流程级总控开关 + 节点级覆盖，生效规则为 AND（流程级关闭则全流程禁用）。

**问题 2（操作语义）**：转办（`setAssignee`）在 MI 节点上的运行时效果与转签（`deleteMultiInstanceExecution` + `addMultiInstanceExecution`）等价，仅审计 action 与权限位不同。转派与转办同义（不同产品叫法），不新增功能。委派（`delegateTask`）语义完全不同（代办不交权、resolve 后任务回原办理人），必须独立保留。收敛方案：前端转办/转签合并为一个"转办"入口，后端按节点是否 MI 自动路由；权限位合并为 `allowTransfer`；委派保留独立按钮与权限位。

**问题 3（部署变化检测）**：`deploy()` 用"改写后 XML（仅含会签/或签改写）"与 `deployedXml` 比较，导致节点/流程配置变化（审批人、操作权限、超时、表单绑定、`__PROCESS__`）不触发部署。收敛方案：变化检测改为 `effectiveBpmnXml + nodeConfigMap（含 __PROCESS__）` 整体 SHA-256 hash 比较，任一变化即可部署，真正无变化才拦截（避免 Flowable 空版本膨胀）。

**问题 5（历史版本查看）**：数据已备齐（Flowable 按版本存 XML、`wf_node_config` 有按 `processDefinitionId` 的配置快照），缺查询 API 与只读视图。收敛方案：新增版本列表 API + 版本编辑器 API（复用 editor 形状）+ 前端只读设计器（bpmn-js 仅渲染 + 属性面板只读模式）。

不在本次范围：问题 4（表单版本管理）、问题 6（底表/业务表单）——按用户指示暂缓，作为已知依赖记录。

## Alternatives Considered

### 方案 A：流程级全局开关 + 节点级覆盖

- **做法**：操作权限（驳回/加签/转办/委派）在流程级 `__PROCESS__` 配置设总开关，节点级 `operations` 保留细调；生效规则 = 流程级 AND 节点级。转办/转签 UI 合并，后端按节点类型自动路由。
- **优点**：管理员可一键收紧全流程操作权限；节点级仍可差异化配置；与主流产品（钉钉/飞书）模式一致。
- **缺点**：流程级开关与节点级开关叠加，配置心智略重；需要后端 `extractOperations` 增加 `__PROCESS__` 叠加解析。
- **为何未采用**：未采用其他方案的原因见下。

### 方案 B：只保留节点级，移除流程级开关

- **做法**：删除 `ProcessProperty.vue` 中废弃的流程级开关（`allowAddSigner`/`allowDelegate`），仅保留节点级 `operations` 作为唯一控制点。
- **优点**：最简单，无叠加逻辑，后端零改动。
- **缺点**：流程管理员无法统一约束操作权限，多个节点需逐个配置；"全公司禁用转办"这类治理需求无法实现。
- **为何未采用**：方案 A 覆盖此场景且成本相近，B 仅适合"无治理需求"的小团队；本项目有多角色（流程设计者/租户管理员）治理需求，A 更合适。

### 方案 C：操作语义彻底统一（转办/转签/委派合并）

- **做法**：删除转签、委派独立入口，统一为"转办"一个操作一个 API，审批记录 action 统一。
- **优点**：概念最简，前端一个按钮，后端一套逻辑。
- **缺点**：委派"代办不交权、resolve 回原办理人"是 `delegateTask` 原生的不同业务流程语义，合并后原办理人拍板权丢失，流程行为改变；审计无法区分"转移"与"临时代办"。
- **为何未采用**：委派与转办是本质不同的业务语义（交权 vs 代办），合并会破坏业务流程正确性。仅转办/转签可合并（同属"交权"，差异仅为 MI 实现细节）。

## Agreed Approach

采用**方案 A**：流程级操作权限总控 + 节点级覆盖（AND 规则）+ 转办/转签 UI 合并后端路由 + 委派独立保留。配套问题 3 的部署检测修复（XML + 配置整体 hash）与问题 5 的历史版本查看（2 个 API + 只读设计器）。

理由：
1. 操作权限是"权限类"配置，天然需要跨节点统一治理；审批人/表单/超时是"内容类"配置，保持节点级。按此原则分层最符合治理需求与产品惯例。
2. 转办/转签合并消除了用户对"会签节点用转签、普通节点用转办"的认知负担，后端路由保留两者审计语义；委派因业务语义不同必须保留。
3. 部署检测 hash 方案同时解决"有效变更被拦截"与"空版本膨胀"两个问题，是问题 1 流程级开关生效的前提。
4. 历史版本查看数据已备齐，API + 只读视图成本可控，且是设计文档中"版本对比（第二期）"的基础。

## Key Decisions

1. **操作权限配置层级**：流程级总控（`__PROCESS__.approvalPolicy.operations`）+ 节点级覆盖（`operations`），生效 = 流程级 AND 节点级；覆盖驳回/加签/转办/委派 4 项（转签并入转办）。
2. **转办/转签合并**：前端合并为一个"转办"入口，后端统一走 `TransferService`（`setAssignee` 天然支持 MI 节点，运行时效果等价于转签）；节点配置移除 `allowForwardSign`，权限位合并为 `allowTransfer`；委派独立保留（`allowDelegate`）。
3. **部署变化检测**：`deployed_config_hash` = SHA-256(effectiveBpmnXml + 序列化 nodeConfigMap（含 `__PROCESS__`）)；部署时比较 hash，变化则允许部署并更新 hash，无变化拦截。
4. **历史版本查看**：新增 `GET /deployed-processes/{key}/versions`（版本列表）与 `GET /deployed-processes/versions/{procDefId}/editor`（该版本 XML + 配置快照）；前端版本历史抽屉 + 只读设计器（bpmn-js 仅渲染 + 属性面板 `readOnly` 模式）。
5. **`__PROCESS__` 配置纳入部署检测**：修复后流程级开关变更可正常部署生效。

## Open Questions

1. **表单版本联动**：问题 4（表单版本管理）本次不做，历史流程版本的"节点关联表单"将显示当前 schema 而非部署时 schema——作为已知限制记录，问题 4 实施后补 `formVersion` 快照。
2. **底表（问题 6）**：本次不做，`wf_form_def` 的 `type` 字段与动态建表方案后续单独变更实施。
3. **历史版本查看的实例联动**：流程实例详情页"查看该实例所用版本配置"入口，是否本次一并实现，或仅做流程管理列表入口（默认仅列表入口，实例联动后续）。
