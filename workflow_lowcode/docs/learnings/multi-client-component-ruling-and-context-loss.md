## 一、必须每次引用的裁决（用户主动提出，非事后补课）

1. **移动端与 WEB 端组件是不同体系**：WEB=Element Plus、移动 H5=Vant 4、
   小程序=uni 内置组件——不能按"一套组件通吃所有端"假设回答任何问题。
2. 因此**不存在"每端一个设计器"**，正确模型是三层分离：
   `页面 schema（语义区块，端无关）→ 按端模板集（EP / Vant / uni）→ 按端运行时`。
   设计入口共用的是**语义 schema 层**，组件差异消化在**渲染层**。
3. **硬约束**：uni-app/Taro 是项目级编译管线，组件无法在管理端运行时动态挂载
   → 平台内所见即所得预览**只能**自建运行时渲染器（iframe 手机框 + Vant）。
   小程序真实效果 = 编译产物 + 开发者工具/真机，没有第三条路。
4. **出码 ≠ 运行时渲染**：两套实现，组件映射表须三列（EP/Vant/uni），存在漂移风险；
   出码线保持独立用途。
5. 现状边界：WEB 模板已实现；移动模板集 + H5 工作台运行时 = **P1 未做**（计划 B1）；
   菜单挂载到移动端分区根（mzone）已打通，但当前只会按 WEB 桌面模板渲染。
6. **权威源文档**：`docs/designs/2026-10-25-多端客户端-菜单组织与页面原型.md` §5
   （§5.1 语义类型×桌面/移动模板对照；§5.2 Vant 能力边界与小程序路线查证结论）。

### 应答规则（防再犯）

- 回答任何"移动端/多端交付/页面设计"问题，**必须先引用本节裁决**，不得默认 WEB-only。
- 给摘要式答复（如"入口在哪"）时，必须带上结论的**前提与边界**（组件分端、运行时未做），
  不许只报路径。

## 二、上下文压缩丢用户输入的坑（过程教训）

- 机制：长会话 checkpoint 压缩时，用户的"提出什么约束 + 为什么坚持"被摘成
  一句结论口径；后续回答只复述结论、丢掉前提，用户输入看起来像被无视。
- **对策：用户主动提出的架构约束、裁决理由，在说出来的当下就落盘**
  （learnings / decisions / ledger 三选一即可，随仓库），不能只留在会话上下文里指望压缩友好。

## 三、同族坑：敏感字面量被渲染打码污染探针（同日事故，一并记录）

- 会话渲染层会把脚本内容里的密码等敏感串打码为 `***`；照打码视图用 write 落盘，
  文件里就是字面 `***` → 探针发出错误凭据 → "后端故障"假象（实测排查了整轮重启/查库/jshell 取证）。
- 对策：**验证脚本涉及凭据/敏感字面量时，一律用 `[char]` 码点拼接构造**，
  并用 `contains` 布尔检查落盘文件实况；后端行为反常时先怀疑自己发出去的字节。
