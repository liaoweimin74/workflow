# 多端客户端支持 — 菜单组织方案与页面原型

> 状态：草案（待评审）
> 日期：2026-10-25
> 关联：多端支持架构分析（客户端 × 渠道 = 数据模型，不限定具体端集合）

---

## 1. 菜单现状（组织方案的出发点）

平台当前是**双轨制**：

- **前端路由静态注册**（`router/index.ts`）：路由与菜单无关，历史页签/收藏不断
- **`sys_menu` 数据树**（0 目录 / 1 菜单 / 2 按钮）：只决定侧边栏显隐 + 权限码；页面渲染权限走 `page:read:{key}` 挂接 + 后端 `PageAccessGuard` 双重校验

V58 归位后的顶层结构：

```
首页 (0)
├─ 开发管理 (1)   表单列表 │ 页面列表 │ 数据源管理 │ 逻辑编排 │ 模块管理 │ 物料管理 │ 菜单管理 │ 数据权限
├─ 样例页面 (2)   组件演示类
├─ 系统管理 (3)   用户管理 │ 角色管理 │ 组织机构 │ 字典管理 │ 岗位管理 │ 成员组管理 │ 模型配置
├─ 流程管理 (4)   流程定义 │ 流程中心 │ 待办处理 │ 草稿箱
└─ 消息管理 (5)   消息中心 │ 模板管理 │ 渠道配置 │ 订阅规则 │ 发送记录 │ 公告管理 │ 事件管理
```

**关键缺口**：整平台只有**一棵菜单树**。"渠道配置"目前指消息通知通道（站内信/短信），与交付终端（WEB/H5/APP/小程序）无关。

## 2. 菜单组织方案

"菜单"在多端语境下有两层含义，分开组织。

### 2.1 平台后台：新功能入口放哪

沿用 V58 既定原则——**按用户任务归目录、能并入现有页的不建新页、path 一律不动**。

| 功能 | 落点 | 理由 |
|---|---|---|
| 客户端管理 | **开发管理 ▸ 客户端管理**（新页面 A1/A2） | 操作对象是"要发布到的端"——与表单列表/页面列表/数据源/菜单管理是同一拨人同一件事（建端→配渠道→设计→发布→挂菜单闭环全在开发管理内）。V66 先例同口径：按"哪拨人干什么事"归目录，不按实体作用域；path 与权限码命名空间不随目录走（同 `/system/menu` 挂开发管理） |
| 客户端菜单配置 | **开发管理 ▸ 菜单管理**（现有页 A3 增强） | 菜单管理已经是拖拽树维护页，加一个"端"作用域切换即可，不另立"客户端菜单管理"页 |
| 资产发布选端 | **页面设计器发布对话框**（A5 扩展） | 发布动作已存在，只增加"目标端"维度，不新增页面 |
| 端身份绑定查看 | **用户管理详情**（A4 新增 Tab） | openid/设备绑定本就是账号属性，V64 `sys_user_openid` 已建在 `sys_user` 之下 |
| 按端授权 | 角色管理（阶段 2，界面不改，数据加维） | 角色 × 端 的默认角色映射收敛到 A2 的"初始授权"区 |

改动后的后台顶层树（🔧 现有页增强，🆕 新页面）：

```
首页
├─ 开发管理   表单列表 │ 页面列表 │ 数据源管理 │ 逻辑编排 │ 模块管理 │ 物料管理 │ 菜单管理🔧 │ 数据权限 │ 客户端管理🆕
├─ 样例页面   （不变）
├─ 系统管理   用户管理🔧 │ 角色管理 │ 组织机构 │ 字典管理 │ 岗位管理 │ 成员组管理 │ 模型配置
├─ 流程管理   （不变）
└─ 消息管理   （不变）
```

**否决的备选**：建一级目录「端接入管理」（客户端 + 开放 API + 主题配置）。当前只有 1-2 个新页面，不足以立目录；且渠道参数配置并入客户端设置抽屉后没有独立页面。后续若"端菜单模板、端主题、发布管线看板"超过 3 页，再升级成目录——path 不动、只挪 `parent_id`，V58 已验证这种迁移成本极低。

### 2.2 运行态：每个客户端自己的菜单

`sys_menu` 增加 `client_id` 作用域（现树全体归默认"平台端"客户端），并按端类型约束形态：

| 端类型 | 菜单形态 | 层级约束 |
|---|---|---|
| WEB / 管理端 | 侧边栏树（现状） | 目录→菜单→按钮 三层（现状规则） |
| H5 / APP / 小程序 | **底部 Tab（2~5 个一级项）+ 工作台宫格** | 工作台内 ≤2 层；按钮继续作为权限节点跟随菜单，不占屏 |

底部 Tab 与工作台不是两套数据：同一棵 `sys_menu(client)` 树，前 N 个一级菜单映射为 Tab，其余挂工作台。

数据模型（新增部分）：

```
sys_client(1) ──< sys_client_channel(N)      端 × 渠道开关与参数（appid/secret/短信…）
sys_menu(client_id 加维)                      每端一棵树，形态按渠道类型校验
wf_page_def ──< page_client_target(N) >── sys_client   页面资产的目标端
sys_user ──< sys_user_openid / sys_user_device >── sys_client  端身份（V64 泛化）
```

### 2.3 存量菜单的处理（归属与定性）

**总原则：现有树 100% 归属默认端"平台客户端"，零破坏迁移。** 迁移只加一列：`sys_menu.client_id`，存量全部回填为平台客户端；path、权限码、角色授权、历史页签一律不动。平台端自此成为众多 Client 中的第一个实例（无特殊代码路径）。

各顶层目录按性质定性：

| 现有目录 | 性质 | 多端模型下的处理 |
|---|---|---|
| 开发管理 | 建造态（平台私有） | 平台端独占，业务端树上不存在这些节点 |
| 样例页面 | 建造态（demo） | 平台端独占 |
| 系统管理 | 混合：**管理界面平台独占，资源全局共享** | 用户/角色/组织/字典的管理页留平台端；`sys_user` 是全端共用账号池（司机/乘客账号就在此维护，与 A2 的"注册默认角色"闭环）。"客户端管理"按 V66 口径归**开发管理**（操作对象是发布目标端，属建造态闭环），不放此目录 |
| 流程管理 | 运行态能力 | 待办/草稿/流程中心是每个端都需要的流程能力，当前仅有 PC 渲染版。各端的移动形态 = 新页面资产（引用同一套流程 API）发布到该端后挂进该端树，**不是**共享 `/process/todo` 这个 PC 页面 |
| 消息管理 | 混合：配置平台独占 / 消息中心运行态 | 模板/渠道/订阅/事件留平台端；消息中心每端各挂各的（移动端 = 顶栏角标 + 列表页） |
| 首页 / 个人中心 | 框架页 | 每端有自己的首页实例（平台端 = 现仪表盘；移动端 = B1 工作台）；个人中心通用、按端形态渲染 |

**核心机制：菜单不复制，能力被引用。**

```
能力资产（表单/页面/流程/消息）──发布勾选目标端（A5）──▶ 端
端菜单树（A3）──挂接该端已发布资产──▶ 用户在该端可见的菜单
```

按钮权限码跨端复用（`process:todo:list` 一类不加端前缀）；端间隔离靠"资产发布范围 × 该端树挂接"两道闸，与现有 `PageAccessGuard` 语义一致，只是校验粒度变为 (client, page)。

### 2.4 权限分层：角色挂端 + 字段级数据范围（已拍板）

**角色按端隔离（拍板：隔离，非白名单）**：

- `sys_role.client_id`（NOT NULL，存量全部回填平台端）：**一个角色记录恰好归属一个端**——"平台端管理员"与"司机端管理员"是两个角色。登录链路校验请求端与角色所属端一致，不一致 = 该端无角色（菜单空 + API 403），错误语义清晰，不存在"配错端导致越权可见"
- 联动：A2"注册默认角色"下拉只列本端角色；角色管理页加"所属端"筛选列；多端通用人员（如运营）= 每端各授一个角色，成本是授权次数，换来的是边界绝对清晰
- 备选"角色 × 允许端 N:N 白名单"已否决：改动小，但配错即越权，与"隔离"诉求不符（本节即拍板记录）

**脱敏并入数据范围（拍板：放数据范围）**：

- v3 现状：受控 = 数据源被权限对象关联；grant =（权限对象 × 主体）只管**行**。扩展：grant 增加**字段策略**（列 → 可见 / 脱敏[引用规则] / 隐藏），缺省跟权限对象基线，实现"行可见但列收紧"
- "乘客看司机"落法：给乘客主体对「司机信息」数据源的 grant 配 `phone→掩码、plate→部分掩、GPS→泛化500m`；规则用平台内置规则集（手机/姓名/身份证/车牌/地理泛化），不进 sys_dict、暂不开放自定义，防配置面成为泄漏面
- **生效点在服务端序列化层**（查询结果 → 渲染/数据/导出 API 出口前），不在 SQL 列选——一次封死详情、导出、开放 API 三条泄漏路径

## 5. Schema 与渲染分层（移动端/WEB 界面区分）

拍板方向：**区分，但区分发生在渲染层与端覆盖层，不发生在资产层。** 三种可能做法里：

| 做法 | 说明 | 判定 |
|---|---|---|
| 同 schema 响应式自适应 | 一套桌面组件 + CSS 断点缩放 | ✗ 表格塞不进 375px，弹窗/工具栏交互模式根本不同，伪移动端 |
| 分端两套资产 | PC 页面、移动页面各建各的 | ✗ 双份维护必然漂移，"发布到端"失去单一事实源 |
| **逻辑 schema 唯一 + 按渠道模板映射 + 端覆盖层** | 一份资产，渲染器按渠道选模板集；设计器可对本端做配置级微调 | ✓ 采用 |

### 5.1 三层区分，各归各位

1. **组件集（渲染器级，平台决定，配置者无感）**：schema 记语义类型，两套渲染器按渠道映射：

| 语义类型 | 桌面模板（现状 Element Plus） | 移动模板（H5，候选 Vant 4） |
|---|---|---|
| 文本/数字/开关输入 | input / input-number / switch | field 系列（单元格式） |
| 下拉/单选/多选 | select / radio / checkbox | picker / radio-group（选项少直出） |
| 日期（范围） | date-picker 弹层 | 滚轮/日历弹层 |
| 文件上传 | upload | uploader（唤相机/相册） |
| 人员·部门选择 | 树形弹窗 | 联系人式钻取页 |
| VIEW 分页表格 | table 列 + 分页器 | **卡片列表** + 下拉刷新/滚动加载 |
| VIEW 筛选区 | 顶部表单行 | 搜索条 + 筛选抽屉 |
| 详情 | 弹窗 | 全屏详情页 / 半屏抽屉 |
| 操作 | 行内按钮组 | 底部动作栏 + 卡片滑动手势 |
| 无移动等价（富文本编辑、复杂透视表） | 正常 | 发布对话框（A5）标记"该端不支持"并拦截 |

2. **布局（配置级，进 schema 的端覆盖层）**：VIEW 显示列 → 卡片槽位（标题/副标题/角标/键值区/主操作），表单默认单列堆叠、并排栅格自动塌缩；设计器加 `[桌面] [移动]` 预览切换，移动端 Tab 只做三件事：**列→槽位映射、字段显隐、排序**。覆盖层按渠道存，缺省自动映射。

3. **交互骨架（框架级，不进 schema）**：弹窗→页面、工具栏→底部栏这类由渲染器框架模板处理。

### 5.2 Vant 能力边界与小程序端路线（查证结论）

- **Vant 4 仅支持 Web/H5**（操作 DOM；官方定位 mobile web apps）。APP 可用是"原生壳 WebView 加载 H5"的间接结果；小程序不可直接用——`@vant/weapp` 是 WXML 自定义组件另一套规范，社区移植（vant-uniapp/@antmjs/vantui）非官方维护
- **uni-app/Taro 不能做平台内预览**：项目级编译管线，组件无法在管理端运行时动态挂载；Taro blended/H5 嵌入模式 Vue3 下有未解决编译 issue 与 DOM API 限制。**平台内所见即所得预览只能靠自建运行时渲染器**（iframe 手机框 + Vant），小程序真实效果 = 编译产物 + 开发者工具/真机
- **uni-app/Taro 可做出码目标**（平台 codegen 线已验证 .vue 产物路线），但出码=编译时渲染，与预览的运行时渲染是两套实现，组件映射表有漂移风险
- **小程序端推荐第三路：运行时壳**。用 uni-app Vue3 做通用"schema 解释器小程序"：壳内固定页面（Tab 容器+通用页容器），渲染器用 uni 内置组件，运行时拉 schema 渲染（微搭/明道云小程序端同模式）。三端统一"运行时渲染"单一模型；出码线保持独立用途。代价：组件映射表三列实现（EP/Vant/uni），壳升级受小程序审核约束

> **2026-10-26 用户复核确认（本案不再开放）**：设计时移动预览采用本节现案——
> iframe 手机框 + **Vant 自建渲染器，可点选编辑（所见即所得）**；设计预览与 H5 生产
> 运行时共用同一 Vant 渲染器（单实现，无端内端外漂移）。uni-app 组件不能进设计画布的
> 原因=项目级编译管线无法动态挂载（本节第二条查证维持）。"iframe 嵌入预览"的记忆与本节
> 一致：iframe 是手机框外壳，壳内渲染的是 Vant。小程序运行时壳归 P2，不回头改 H5 线。

### 5.3 前置风险：存量 schema 的桌面细节审计

现 schema（VIEW 配置 / form-create rule）里混着桌面渲染细节（列宽、栅格 span、弹窗尺寸）。**P0 需先做一次 spike**：逐组件清点哪些是语义（字段、动作、校验）、哪些是表现（宽度/尺寸/位置），表现字段迁到渠道 profile 层，否则移动渲染器会被迫读不懂的遗留属性。
